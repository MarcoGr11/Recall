## Аналітичний висновок підрозділу 1.2

Проаналізовані аналоги реалізують два протилежні архітектурні підходи. Moodle — централізований монолітний PHP-застосунок, у якому важкі операції (зокрема старт спроб тестування групою) виконуються синхронно в межах HTTP-запиту, а фонова обробка залежить від інтервалу запуску cron і зберігає чергу задач у реляційній БД; двонаправлений канал передачі даних у ядрі відсутній. Anki — local-first застосунок з плануванням повторень на клієнті та синхронізацією колекції SQLite, що виключає серверну координацію: модель даних не містить сутностей групи і викладача, а розклад повторень обчислюється для кожної картки без урахування дат іспитів кількох дисциплін. Quizlet, за публічно доступними даними, мав проблему масштабування запису в MySQL, яку розв'язував шардуванням і реплікацією, проте інженерних даних про асинхронну обробку і real-time канал не опубліковано. Таким чином, жоден з аналогів не поєднує серверну координацію розкладу повторень між дисциплінами, асинхронну обробку ресурсоємних задач і двонаправлений канал моніторингу групи.

Для Recall обрано модульний моноліт на Node.js і Express. Це рішення є свідомим компромісом: за соло-розробки та цільового навантаження в межах однієї групи чи потоку мікросервісна декомпозиція збільшує операційну складність без пропорційного виграшу, а горизонтальне масштабування рівня Moodle не є метою проєкту. Вузькі місця, виявлені в аналогах, усунено точково. Ресурсоємні та ненадійні операції (виклики Claude API, парсинг лекційних PDF) винесено з циклу HTTP-запиту в чергу BullMQ на Redis з повторними спробами, експоненційною затримкою та dead-letter queue, що ізолює Latency зовнішнього API від REST-шару. Моніторинг засвоєння реалізовано через WebSocket (Socket.io) замість періодичного опитування. Розклад повторень за алгоритмом SM-2 обчислюється на сервері з пріоритизацією за датами іспитів, що можливо лише за централізованого зберігання даних усіх дисциплін студента в PostgreSQL з транзакційною консистентністю.

Обмеження обраного підходу полягають у відсутності кластеризації backend на етапі MVP та в залежності черги від доступності Redis; ці обмеження відповідають заявленому масштабу і фіксуються як напрями розвитку. Визначені вимоги до асинхронного конвеєра генерації, real-time каналу та серверного планування повторень є вихідними даними для проєктування архітектури системи, моделі даних і протоколів взаємодії компонентів, що розглядаються в Розділі 2.
