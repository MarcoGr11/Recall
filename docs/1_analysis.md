## 1.2 Аналіз програмних аналогів

Для аналізу обрано три програмні системи, що розв'язують суміжні задачі: систему управління навчанням Moodle та застосунки інтервального повторення Anki і Quizlet. Аналоги розглянуто як інженерні системи за архітектурним патерном, протоколами обміну даними, стеком зберігання даних і механізмами консистентності, а також за відомими технічними обмеженнями. Відомості про відкриті системи отримано з офіційної документації та вихідного коду; для закритої системи Quizlet використано публічні інженерні матеріали, а положення без документального підтвердження позначено як архітектурні припущення.

Moodle є монолітним вебзастосунком на PHP з плагінною архітектурою. Горизонтальне масштабування здійснюється кластером ідентичних вузлів за балансувальником навантаження за умови спільного ACID-сумісного сервера БД (PostgreSQL, MySQL, MariaDB, Microsoft SQL Server), спільного файлового каталогу `dataroot` і централізованого сховища сесій та кешу MUC (Redis або Memcached). Взаємодія з клієнтами виконується через HTTP із серверним рендерингом, AJAX-виклики External API та web services за протоколами REST і SOAP; протокол XML-RPC вилучено з ядра у версії 4.1. Фонова обробка реалізована через Task API із запуском задач процесом cron, черга задач зберігається в реляційній БД. Транспорт WebSocket у ядрі відсутній: двонаправлена доставка подій можлива лише через сторонній плагін `tool_realtime`. До технічних обмежень належать синхронна обробка пікових операцій у межах HTTP-запиту (одночасний старт спроб тестування групою), залежність гранулярності фонової обробки від інтервалу cron, спільний `dataroot` як точка відмови кластера та серіалізація запитів одного користувача блокуванням сесії.

Anki є local-first настільним застосунком із шаруватою архітектурою: основну логіку реалізовано бібліотекою rslib на Rust, над нею розташовано Python-шари pylib і aqt (Qt) та вебкомпоненти на TypeScript; обмін між шарами виконується через Protocol Buffers. Колекція користувача зберігається в локальній базі SQLite, розклад повторень обчислюється на клієнті за алгоритмом SM-2 або FSRS (FSRS інтегровано в ядро з версії 23.10). Сервер AnkiWeb виконує лише функцію синхронізації через нестандартизований HTTP(S)-протокол: звичайна синхронізація об'єднує зміни з різних пристроїв, а після змін схеми колекції застосовується одностороння повна синхронізація зі збереженням даних лише однієї сторони. Модель даних не містить сутностей групи, курсу і викладача, тому серверне агрегування прогресу та координація розкладу повторень між дисциплінами з різними датами іспитів архітектурно не передбачені.

Quizlet є закритою централізованою вебсистемою. За публічно доступними даними, серверну частину побудовано на PHP і MySQL, у 2015 році інфраструктуру перенесено на Google Compute Engine; система обслуговує вебсайт і HTTP API мобільних застосунків. Масштабування СУБД здійснювалося вертикальним шардуванням і перенесенням читання на репліки MySQL; у 2017 році компанія оприлюднила, що цей підхід досягає межі, оскільки окремі таблиці перевищують ємність одного шарда, і тестувала Cloud Spanner. Задокументованим технічним обмеженням є масштабування запису в реляційну СУБД за шестикратного сезонного зростання трафіку. Відомості про асинхронну обробку задач, реалізацію real-time каналу групових режимів і алгоритм повторення в публічних інженерних джерелах відсутні.

Аналоги реалізують два протилежні архітектурні підходи. У Moodle ресурсоємні операції виконуються синхронно в межах HTTP-запиту, фонова обробка залежить від інтервалу запуску cron, а двонаправлений канал передачі даних у ядрі відсутній. В Anki планування повторень виконується на клієнті, що виключає серверну координацію: модель даних не містить сутностей групи і викладача, а розклад обчислюється без урахування дат іспитів кількох дисциплін. Для Quizlet публічно задокументовано обмеження масштабування запису в MySQL, тоді як дані про асинхронну обробку і real-time канал не опубліковано. Жоден з проаналізованих аналогів не поєднує серверну координацію розкладу повторень між дисциплінами, асинхронну обробку ресурсоємних задач і двонаправлений канал моніторингу групи.

Для Recall обрано архітектуру модульного моноліту на Node.js і Express. Рішення зумовлене умовами соло-розробки та цільовим навантаженням у межах однієї групи або потоку, за яких мікросервісна декомпозиція збільшує операційну складність без пропорційного виграшу; горизонтальне масштабування рівня Moodle не є метою проєкту. Вузькі місця, виявлені в аналогах, враховано в окремих архітектурних рішеннях. Ресурсоємні операції із залежністю від зовнішніх сервісів (виклики Claude API, парсинг лекційних PDF) винесено з циклу HTTP-запиту в чергу BullMQ на Redis з повторними спробами, експоненційною затримкою та dead-letter queue, що ізолює Latency зовнішнього API від REST-шару. Для моніторингу засвоєння передбачено канал WebSocket (Socket.io) замість періодичного опитування сервера. Розклад повторень за алгоритмом SM-2 обчислюється на сервері з пріоритизацією за датами іспитів, що потребує централізованого зберігання даних усіх дисциплін студента в PostgreSQL з транзакційною консистентністю.

Обмеженнями обраного підходу є відсутність кластеризації backend на етапі MVP та залежність черги від доступності Redis; їх зафіксовано як напрями подальшого розвитку системи. Визначені вимоги до асинхронного конвеєра генерації, real-time каналу та серверного планування повторень є вихідними даними для проєктування архітектури системи, моделі даних і протоколів взаємодії компонентів у Розділі 2.
