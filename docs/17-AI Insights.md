## Запис 1 — Валідація першої теми Retain (15.09.2026)

### Як розвивалась ідея (ключові точки, а не лінійний план)

- Початкова ідея — військовий застосунок з 3D-анімаціями медичних процедур; звужено до конкретної аудиторії (БЗВП) і конкретної офіційної програми (Типова програма Генштабу, 24.02.2025) після перевірки, що саме за нею навчають у виші
- Розглянуто і відхилено: повний офлайн-режим (виявилось зайвим — заняття проходять у обладнаних класах зі стабільним інтернетом), ML-розпізнавання дронів через камеру як кілер-фіча (обрано натомість сценарний тренажер — реалістичніше за 6 місяців соло-розробки)
- Кілер-фіча (AI-генерація сценаріїв) обрана з трьох варіантів (ML-розпізнавання / сценарії / аудіо-розпізнавання) свідомо як найменш технічно ризикована при збереженні "вау-ефекту"
- Окремо обговорювалось і залишено відкритим питання: WebSocket vs простий HTTP-polling для дашборду інструктора — обрано WebSocket свідомо заради демонстраційного ефекту на захисті, а не з технічної необхідності (для масштабу однієї групи різниця в затримці некритична)

### Промпт для валідації (за шаблоном методички, з реальним наповненням)

Використано розширений (жорсткіший) варіант шаблону методички — "під еталонні архітектурні рішення", оскільки базовий варіант дає надто загальну відповідь без конкретики.

> Core Features: рольова модель на рівні курсу (owner/co-instructor/cadet),
> SM-2-повторення, live-дашборд, підтвердження засвоєння, сценарний тренажер

### Критичні зауваження ШІ, а не тільки схвалення

- **Ризик обсягу**: повний стек (мобільний застосунок + backend + WebSocket + SM-2 + AI-конвеєр + DevOps) для соло-розробки за 6 місяців — оптимістична оцінка; рекомендовано чітко звузити MVP і бути готовим свідомо відрізати частину Should Have функцій ближче до дедлайну, а не намагатись зробити все заплановане
- **Ризик джерел контенту**: для модулів "Вогнева підготовка", "Тактична підготовка", "Розвідувальна підготовка" відкритих джерел недостатньо для якісного наповнення — потрібна консультація практика, інакше контент буде поверхневим
- **Питання коректності**: у первинному чорновому формулюванні актуальності помилково приписано вимогу використання Moodle офіційній типовій програмі Генштабу — насправді це лише практика конкретного закладу освіти, а не пункт офіційного документа. Виправлено до подання керівнику
- **Термінологічна неточність**: цикл "AI генерує → інструктор перевіряє" початково описано як "машинне навчання" — вказано, що модель не тренується і не змінює поведінку, точніший термін — "конвеєр генерації та курації контенту"

### Рекомендації щодо підсилення архітектурної складності (опційно, не реалізовано в MVP)

- Read replica PostgreSQL — розділення навантаження читання/запису
- Базовий Observability (Prometheus/Grafana) для метрик черги генерації
- Формалізація ADR (Architecture Decision Records) для ключових рішень (WebSocket vs polling, Redis vs RabbitMQ)

### Що змінилось в результаті

- Формулювання актуальності виправлено (розділено зміст програми і практику LMS конкретного вишу)
- До стеку додано Docker/docker-compose, GitHub Actions CI, чергу Redis+BullMQ — саме як реакція на вимогу методички "не простий CRUD-сайт"
- Фінальний варіант зафіксовано у `docs/proposal.md` та у `thesis_proposal.docx`, надісланому науковому керівнику 15.09.2026

- Observability: метрики черги (довжина, час обробки, частка помилок) через Prometheus + Grafana.
- ADR для ключових рішень: моноліт проти мікросервісів, WebSocket проти polling, BullMQ проти RabbitMQ.

> Перехід на мікросервісну архітектуру — для соло-розробки за 6 місяців ризик не встигнути переважає архітектурну вигоду; моноліт з виокремленою асинхронною обробкою достатній для заявленого масштабу.
