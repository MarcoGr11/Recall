## Запис 1 — Валідація першої теми Retain (15.09.2026)

### Як розвивалась ідея (ключові точки, а не лінійний план)

- Початкова ідея — військовий застосунок з 3D-анімаціями медичних процедур; звужено до конкретної аудиторії (БЗВП) і конкретної офіційної програми (Типова програма Генштабу, 24.02.2025) після перевірки, що саме за нею навчають у виші
- Розглянуто і відхилено: повний офлайн-режим (виявилось зайвим — заняття проходять у обладнаних класах зі стабільним інтернетом), ML-розпізнавання дронів через камеру як кілер-фіча (обрано натомість сценарний тренажер — реалістичніше за 6 місяців соло-розробки)
- Кілер-фіча (AI-генерація сценаріїв) обрана з трьох варіантів (ML-розпізнавання / сценарії / аудіо-розпізнавання) свідомо як найменш технічно ризикована при збереженні "вау-ефекту"
- Окремо обговорювалось і залишено відкритим питання: WebSocket vs простий HTTP-polling для дашборду інструктора — обрано WebSocket свідомо заради демонстраційного ефекту на захисті, а не з технічної необхідності (для масштабу однієї групи різниця в затримці некритична)

### Критичні зауваження ШІ, а не тільки схвалення

- **Ризик обсягу**: повний стек (мобільний застосунок + backend + WebSocket + SM-2 + AI-конвеєр + DevOps) для соло-розробки за 6 місяців — оптимістична оцінка; рекомендовано чітко звузити MVP і бути готовим свідомо відрізати частину Should Have функцій ближче до дедлайну, а не намагатись зробити все заплановане
- **Ризик джерел контенту**: для модулів "Вогнева підготовка", "Тактична підготовка", "Розвідувальна підготовка" відкритих джерел недостатньо для якісного наповнення — потрібна консультація практика, інакше контент буде поверхневим
- **Питання коректності**: у первинному чорновому формулюванні актуальності помилково приписано вимогу використання Moodle офіційній типовій програмі Генштабу — насправді це лише практика конкретного закладу освіти, а не пункт офіційного документа. Виправлено до подання керівнику
- **Термінологічна неточність**: цикл "AI генерує → інструктор перевіряє" початково описано як "машинне навчання" — вказано, що модель не тренується і не змінює поведінку, точніший термін — "конвеєр генерації та курації контенту"

### Рекомендації щодо підсилення архітектурної складності (опційно, не реалізовано в MVP)

- Read replica PostgreSQL — розділення навантаження читання/запису
- Базовий Observability (Prometheus/Grafana) для метрик черги генерації
- Формалізація ADR (Architecture Decision Records) для ключових рішень (WebSocket vs polling, Redis vs RabbitMQ)

### Що змінилось в результаті

- Формулювання актуальності виправлено (розділено зміст програми і практику LMS конкретного вишу)
- До стеку додано Docker/docker-compose, GitHub Actions CI, чергу Redis+BullMQ — саме як реакція на вимогу методички "не простий CRUD-сайт"

>

### Хід сесії

- Пункт 1 шаблону методички («які рішення аналогів застарілі») підштовхує до протиставлення «застарілий моноліт Moodle — сучасна архітектура Recall». Таке протиставлення некоректне, оскільки Recall також є монолітом, а масштаб Moodle (кластер для всього університету) не є метою проєкту. Тому блок «Обмеження» додано до промпту одразу, до першого запуску.
- Отриманий висновок сформулював компроміс: модульний моноліт обрано свідомо для соло-розробки і масштабу однієї групи чи потоку; вузькі місця аналогів (синхронна обробка важких задач, відсутність real-time каналу, відсутність серверної координації розкладу між дисциплінами) винесено в BullMQ і WebSocket.
- Окремі формулювання висновку («усунено», «реалізовано», «свідомим компромісом») надто категоричні для системи на етапі проєктування; їх виправлено на етапі лінтингу (Запис 7).
- Для Quizlet висновок спирається лише на підтверджене обмеження (масштабування запису в MySQL), без припущень про внутрішню архітектуру.

> [!failure] Відкинуто

### Хід сесії (калібрування метрик)

| Було | Стало | Причина |
|---|---|---|
| «Основні екрани завантажуються швидко, не більше 2 сек» (NFR-01 з [[04-Нефункціональні вимоги]]) | p95 Latency REST API ≤ 300 мс (читання) і ≤ 500 мс (запис) при 50 RPS | метрика серверного API вимірюється k6; час рендерингу клієнта винесено в окрему вимогу (холодний старт ≤ 3 с) |
| «Затримка WebSocket-оновлення не більше кількох секунд» | p95 ≤ 1 с при 100 одночасних з'єднаннях | «кілька секунд» не перевіряється |
| Цільове навантаження 500 RPS, OAuth 2.0 / OIDC (з прикладу методички) | 50 RPS; власна автентифікація на JWT (access 15 хв, refresh 30 днів з ротацією) | навантаження розраховано для апробації на одному потоці (до 100 студентів); зовнішній провайдер ідентичності на MVP не використовується |

> ## 5. Glossary
>
> | Термін | Визначення |
> |---|---|
> | SM-2 | Алгоритм інтервального повторення SuperMemo-2 (P. Woźniak, 1987), який за оцінкою якості відповіді q ∈ {0…5} обчислює інтервал до наступного повторення і коефіцієнт легкості; при q < 3 лічильник повторень скидається, інтервал повертається до 1 дня |
> | Ease Factor (EF) | Коефіцієнт легкості SM-2, що визначає множник інтервалу: EF′ = EF + (0,1 − (5 − q) · (0,08 + (5 − q) · 0,02)); початкове значення 2,5, мінімальне 1,3 |
> | p95 Latency | 95-й перцентиль часу відповіді: значення, яке не перевищують 95 % вимірів за інтервал тестування |
> | BullMQ | Бібліотека черг задач для Node.js, що зберігає стан задач у Redis і підтримує повторні спроби, відкладене виконання та обмеження паралелізму обробників |
> | Dead-letter queue | Сховище задач, обробку яких завершено помилкою після вичерпання допустимої кількості спроб; задачі в ньому автоматично не повторюються і підлягають ручному аналізу |
> | JWT | JSON Web Token (RFC 7519) — підписаний токен із набором тверджень (claims), що передає ідентичність і строк дії сесії без звернення до сховища сесій |
> | WebSocket | Протокол повнодуплексного обміну повідомленнями поверх одного TCP-з'єднання, встановленого через HTTP Upgrade (RFC 6455); у системі використовується через бібліотеку Socket.io з механізмом кімнат |
> ```

> Позначення рівня: [BLOCKER] — вимога не верифікується або суперечить іншій; [MAJOR] — неповнота, що впливає на проєктування; [MINOR] — оформлення.

> ### 1. Критика атомарності та чіткості функціональних вимог
>
> **A-01 [MAJOR] SRS-FUN-01 — порушення singular.** Одна вимога містить чотири: реєстрація; автентифікація за access/refresh JWT; призначення ролі в курсі; приєднання за кодом запрошення. Не визначено атрибути коду запрошення: строк дії, кількість використань, роль, що призначається. Рекомендація: розбити на 4 вимоги; додати параметри коду (строк дії, `role_to_assign`).
>
> **A-02 [BLOCKER] SRS-FUN-02 — порушення singular і consistent.** Поєднано створення курсу і завантаження PDF. Атрибут «дата іспиту» суперечить SRS-FUN-14 (курс має кілька контрольних заходів). Параметри «перевірки типу й розміру» відсутні у тексті вимоги і наявні лише в SRS-NFR-SEC-03 — дублювання з ризиком розбіжності. Рекомендація: курс — назва, теми; дати переносяться в контрольні заходи; завантаження PDF — окрема вимога з посиланням на SEC-03.
>
> **A-03 [BLOCKER] SRS-FUN-03 — порушення singular і unambiguous.** Три дії: видача з рандомізацією, фіксація відповіді, обчислення оцінки якості. Правило обчислення q ∈ {0…5} не визначено: для тесту з вибором варіанта система отримує лише бінарний результат (правильно/неправильно) і час відповіді. Без таблиці відображення вимога не верифікується, а SRS-FUN-04 отримує невизначений вхід. Рекомендація: задати детерміновану функцію q = f(correct, час відповіді, використання підказки) у вигляді таблиці.
>
> **A-04 [MINOR] SRS-FUN-04 — змішування функціональної і нефункціональної вимоги.** Транзакційність дублює SRS-NFR-REL-01. Не задано початкові параметри SM-2 (EF₀ = 2,5, EF_min = 1,3) і гранулярність стану (студент × тема чи студент × питання). Рекомендація: залишити функцію перерахунку, транзакційність — тільки в REL-01; додати параметри з посиланням на Глосарій.
>
> **A-05 [BLOCKER] SRS-FUN-05 — порушення unambiguous, verifiable, consistent.** «Пріоритизуючи за близькістю дати іспиту та простроченням» — формула пріоритету відсутня, ваги факторів не визначено, денний ліміт обсягу (наявний у моделі To-Be) не перенесено. Суперечність із SRS-FUN-14: вимога посилається на дату іспиту, а не на найближчий контрольний захід. Рекомендація: задати формулу пріоритету теми і денний ліміт як параметр; джерело дати — найближчий контрольний захід, що містить тему.
>
> **A-06 [MAJOR] SRS-FUN-06 — порушення singular.** Вимога містить щонайменше шість дій: постановка задачі, виконання worker-процесом, валідація, збереження чернетки, схвалення, редагування, відхилення. Не визначено: схему валідації результату (JSON Schema / zod), поведінку при невалідному результаті (повторна спроба чи помилка без повторення), подію завершення задачі для викладача. Сценарний тренажер заявлено в Scope, проте окремої вимоги немає — порушення completeness. Рекомендація: розбити на вимоги «постановка», «обробка», «валідація», «модерація»; додати вимогу для типу контенту «сценарій».
>
> **A-07 [MAJOR] SRS-FUN-07 — порушення singular, verifiable.** Трансляція подій і відображення дашборду — дві вимоги. «В реальному часі» без посилання на SRS-NFR-RT-01 не верифікується. Не визначено склад події прогресу і правило авторизації підписки на кімнату курсу: студент не повинен отримувати події інших студентів. Рекомендація: розбити; додати перелік полів події; додати вимогу авторизації підписки.
>
> **A-08 [MAJOR] SRS-FUN-08 — порушення singular, unambiguous.** Теплова карта і підтвердження засвоєння — дві вимоги. Метрика засвоєння клітинки «студент × тема» не визначена (частка правильних відповідей, EF, кількість повторень). Не визначено, які ролі можуть підтверджувати засвоєння, і чи журналюється дія (`confirmed_by`, час).
>
> **A-09 [MAJOR] SRS-FUN-09 — неповнота.** Не визначено формат зразка (PDF, структурований JSON), прив'язку зразка до контрольного заходу і ролі, що мають доступ. Формулювання «не передавані на клієнт» є обмеженням безпеки і має бути окремою вимогою з методом перевірки.
>
> **A-10 [BLOCKER] SRS-FUN-10 — порушення verifiable.** «Перевірка на подібність до оригіналу» не має метрики і порогу. Кількість варіантів на питання (2–3, з джерела BR-17) не перенесено. Не визначено, що відбувається з варіантом, який перевищив поріг. Рекомендація: формалізувати метрику (наприклад, коефіцієнт Жаккара на триграмах слів після нормалізації або косинусна подібність ембеддингів), поріг відхилення і дію «відкинути без показу викладачу».
>
> **A-11 [BLOCKER] SRS-FUN-11 — порушення unambiguous, feasible.** «Структура реального тесту» не визначена (кількість питань за темами і типами). «Новий набір питань для кожної спроби» не здійсненний при скінченному пулі схвалених питань. Рекомендація: структура = кількість питань за кожною темою і типом зразка; правило неповторення — питання не повторюється в N попередніх спробах студента, якщо пул достатній; мінімальний розмір пулу як передумова публікації пробного тесту.
>
> **A-12 [MAJOR] SRS-FUN-12 — порушення singular, unambiguous.** Фіксація і показ — дві вимоги. «Вихід із застосунку» технічно не визначено: на iOS стан `inactive` виникає при відкритті Центру керування і сповіщень, що дає хибні спрацювання. Не визначено поведінку при втраті з'єднання в момент виходу (буферизація подій на клієнті та доставка після відновлення).
>
> **A-13 [MAJOR] SRS-FUN-13 — порушення singular, conforming.** Три вимоги з платформозалежною поведінкою в одному реченні. Модальне дієслово «має» відрізняється від «повинна» в інших вимогах — набір не однорідний за формою. Для iOS не визначено, що є результатом «фіксації» (подія на сервер, показ викладачу).
>
> **A-14 [MAJOR] SRS-FUN-14 — порушення singular.** Підтримка контрольних заходів і їх урахування в пріоритизації — дві вимоги; друга дублює SRS-FUN-05.
>
> **A-15 [MAJOR] Атрибути вимог (п. 5.2.8).** Відсутні обов'язкові для трасування атрибути: пріоритет (MoSCoW або Must/Should/Could), метод верифікації (Inspection / Analysis / Demonstration / Test), джерело (наявне), стан. Рекомендація: таблична форма або рядок атрибутів під кожною вимогою.
>
> **A-16 [MINOR] Модальність.** Використати одне модальне дієслово для обов'язкових вимог («повинна»), еквівалент «shall» за п. 5.2.4.

> ### 2. Аудит вимірюваності NFRs
>
> **N-01 [MAJOR] SRS-NFR-PERF-01/02.** Відсутні умови вимірювання: апаратна конфігурація хоста docker-compose, обсяг даних у БД на момент тесту, тривалість сталого навантаження, перелік ендпоінтів. Для PERF-02 відсутній поріг частки помилок. Без умов p95 не відтворюється.
>
> **N-02 [MAJOR] SRS-NFR-RT-01.** Не визначено точки вимірювання (commit транзакції → отримання події клієнтом) і спосіб усунення розбіжності годинників (вимірювання на одному хості або за серверною міткою часу). 100 з'єднань при 50 одночасних сесіях потребує пояснення складу з'єднань.
>
> **N-03 [MAJOR] SRS-NFR-ASYNC-02.** Метрика p95 ≤ 90 с включає Latency зовнішнього провайдера, яку система не контролює. «До 3 спроб» неоднозначне: 3 спроби загалом чи 3 повтори. Не задано базову затримку backoff, timeout одного виклику Claude API, обробку відповіді 429 / 529 провайдера. Вимога є складеною (час, повтори, DLQ, паралелізм).
>
> **N-04 [MAJOR] SRS-NFR-SEC-01.** Складена вимога (строки токенів, ротація, хешування). Ротація refresh-токена без виявлення повторного використання (reuse detection) не захищає від викраденого токена. Не визначено сховище токенів на клієнті (expo-secure-store / Keychain / Keystore).
>
> **N-05 [MAJOR] SRS-NFR-SEC-02.** Не охоплює канал WebSocket: авторизація handshake Socket.io і приєднання до кімнати курсу. Не визначено поведінку для неіснуючого ресурсу (403 чи 404 — ризик розкриття існування ресурсу).
>
> **N-06 [BLOCKER] SRS-NFR-SEC-03.** (а) Складена вимога (TLS, rate limit, завантаження файлів). (б) TLS 1.2+ не реалізовний поточною інфраструктурою: у docker-compose немає компонента термінації TLS, backend публікує порт 3000 у відкритому вигляді; також PostgreSQL 5432 і Redis 6379 опубліковані на хост. (в) Ліміт 100 запитів/хв на IP хибно блокує групу студентів за NAT університетської мережі (один зовнішній IP на 100 користувачів). (г) Не визначено відповідь при перевищенні (429, Retry-After) і поведінку для великого файлу (413) та неприпустимого типу (415).
>
> **N-07 [MAJOR] SRS-NFR-SEC-04.** «Відповідність OWASP Top 10» неверифікована як ціле; перевіряються лише наслідки сканування. Умова за замовчуванням Quality Gate «Sonar way» (покриття нового коду ≥ 80 %) суперечить SRS-NFR-MAINT-01 (70 %). Рекомендація: визначити власний Quality Gate з умовами.
>

> ### 3. Валідація критеріїв верифікації
>
> **V-01 [MAJOR] k6.** Сценарії не містять формалізованих порогів (`thresholds`) у вигляді pass/fail. Рекомендація: `http_req_duration{type:read}: p(95)<300`, `http_req_failed: rate<0.01`; executor `constant-arrival-rate` для Load і `ramping-arrival-rate` для Spike.
>
> **V-02 [MAJOR] SRS-NFR-RT-01 через k6 WebSocket.** Модуль k6 WebSocket працює з «сирим» протоколом; Socket.io використовує власний протокол Engine.IO поверх WebSocket (handshake, пакети `40`, `42[...]`, ping/pong). Сценарій потребує ручної реалізації протоколу. Рекомендація: окремий Node.js-скрипт навантаження на `socket.io-client` з вимірюванням за серверною міткою часу, або k6 з ручним кодуванням кадрів Engine.IO — з фіксацією обраного методу.
>
> **V-03 [BLOCKER] SRS-NFR-ASYNC-02 — «журнал черги BullMQ».** Журнал не є методом верифікації: сценарії повторних спроб і DLQ не відтворюються на вимогу. Рекомендація: інтеграційний тест Jest з підміною Claude API (nock / MSW) з керованими відмовами (timeout, 429, невалідний JSON) і перевіркою кількості спроб, затримок і переходу в failed / DLQ.
>
> **V-04 [MAJOR] SRS-NFR-REL-02.** Не визначено періодичність тестового відновлення і критерій успіху (кількість рядків ключових таблиць, контрольні суми, тривалість ≤ RTO).
>
> **V-05 [MAJOR] Доступність.** Ручний прохід без чекліста не відтворюється. Рекомендація: чекліст екранів і елементів; додатково статична перевірка `eslint-plugin-react-native-a11y` і тести React Native Testing Library із запитами за `accessibilityRole` / `accessibilityLabel`.
>
> **V-06 [MAJOR] Відсутні критерії для SRS-FUN-01…03, 05…14.** Верифікацію визначено лише для однієї функціональної вимоги (SRS-FUN-04). SRS-FUN-13 не перевіряється в CI — необхідний ручний тест на фізичних пристроях Android та iOS з фіксацією моделі й версії ОС.
>
> **V-07 [MAJOR] Матриця трасування.** Відсутній зв'язок «вимога → тест-кейс / сценарій». Рекомендація: стовпець «Метод» (I/A/D/T) і ідентифікатор сценарію перевірки для кожної вимоги.
>
> **V-08 [MINOR] SRS-NFR-SEC-04.** Не визначено умову блокування Pull Request (обов'язковий status check) — без неї порушення не блокує злиття.

> ### 1. Аудит відповідності SRS та трасування
>
> **C-01 [MAJOR] Співвикладач відсутній на Level 1.** SRS, п. 1.3, визначає трьох людських акторів. Діаграма об'єднує owner і co-instructor в «Викладач» без пояснення. Рекомендація: позначити «Викладач (owner, co-instructor)» або показати окремого Person.
>
> **C-02 [BLOCKER] Мобільна ОС відсутня як зовнішня система.** SRS-FUN-37 (AppState), SRS-FUN-40, SRS-FUN-41 (захист екрана), SRS-NFR-SEC-04 (Keystore / Keychain), SRS-NFR-A11Y-02 (TalkBack / VoiceOver) залежать від API ОС. На Level 1 і Level 2 немає вузла, що реалізує ці вимоги.
>
> **C-03 [BLOCKER] Термінація TLS відсутня.** SRS-NFR-SEC-06 вимагає HTTPS/WSS з TLS 1.2+ на reverse proxy і публікації лише порту 443. На Level 2 клієнт звертається до Backend API напряму; контейнер reverse proxy відсутній.
>
> **C-04 [BLOCKER] Канал real-time не змодельовано.** Зв'язок Mobile App → Backend API підписано «Запити» без розрізнення REST і WebSocket. SRS-FUN-43…SRS-FUN-45 і SRS-NFR-RT-01 не мають явного носія.
>
> **C-05 [BLOCKER] Подія завершення генерації не має шляху доставки.** SRS-FUN-30 вимагає події WebSocket викладачу після завершення задачі. Socket.io працює в процесі Backend API, задача завершується в Generation Worker; зв'язку Worker → API (через Redis: BullMQ QueueEvents або pub/sub) на діаграмі немає.
>
> **C-06 [MAJOR] Сховище файлів відсутнє.** SRS-FUN-09, SRS-FUN-10 (PDF лекцій і зразків) потребують файлового сховища, доступного Backend API на запис і Generation Worker на читання. Без нього незрозуміло, як worker отримує вміст PDF.
>
> **C-07 [MAJOR] Резервне копіювання відсутнє.** SRS-NFR-REL-03 (щоденний pg_dump, копія на окремому носії) не має виконавця на Level 2.
>
> **C-08 [MAJOR] Таблиця трасування відсутня.** Діаграми не супроводжуються переліком «вузол → SRS-ID»; повноту покриття 49 SRS-FUN неможливо перевірити інспекцією.
>
> **C-09 [MINOR] Інтеграція LTI 1.3.** SRS, п. 1.2, відносить LTI 1.3 до поза-MVP. Рекомендація: не показувати LMS або показати пунктиром із підписом «LTI 1.3 (поза MVP)», щоб межа системи була явною.
>
> **C-10 [MINOR] CI/CD-контур.** GitHub Actions, SonarQube Cloud, Trivy не є елементами runtime і коректно відсутні на Level 2; рекомендовано зазначити це в тексті, щоб SRS-NFR-SEC-09…SEC-11 мали посилання на розділ розгортання.
>
> ---
>
> ### 2. Аналіз архітектурної логіки контейнерів (Level 2)
>
> **C-11 [MAJOR] Відповідальність Backend API не деталізована.** Опис «REST API і real-time події» не відображає модулів модульного моноліту (auth, courses, testing, scheduling, generation, monitoring). Рекомендація: перелік модулів в описі контейнера; деталізація — Level 3.
>
> **C-12 [MAJOR] Спільна база даних API і Worker.** Обидва контейнери пишуть у PostgreSQL. Для модульного моноліту з одним кодовим репозиторієм це допустимо за умови, що worker використовує ті самі репозиторії і схему; рішення треба зафіксувати явно, інакше діаграма читається як порушення принципу database-per-service.
>
> **C-13 [MAJOR] Роль Redis описано неповно.** Redis виконує функції брокера черги BullMQ і каналу подій задач (QueueEvents на основі Redis Streams). Опис «Черга задач» не охоплює другу функцію.
>
> **C-14 [MINOR] Один клієнтський контейнер для двох ролей.** Mobile App обслуговує і студента, і викладача — коректно для рольового інтерфейсу; рекомендовано зазначити в описі.
>
> **C-15 [MAJOR] API Gateway.** Для Enterprise-архітектур 2026 року рекомендовано виділений API Gateway (Kong, Traefik з middleware) для централізованого rate limiting, автентифікації і маршрутизації.
>
> **C-16 [MAJOR] Identity Provider.** Рекомендовано винести автентифікацію в окремий контейнер Identity Provider (Keycloak, OIDC) замість модуля Backend API.
>
> ---
>
> ### 3. Перевірка інженерних зв'язків та протоколів
>
> **C-17 [BLOCKER] Протоколи не вказано на жодному зв'язку.** Рекомендовані підписи:
> - Mobile App → Reverse Proxy: REST/HTTPS (JSON); WSS (Socket.io);
> - Reverse Proxy → Backend API: HTTP/1.1, WebSocket Upgrade (внутрішня мережа);
> - Backend API → PostgreSQL, Generation Worker → PostgreSQL: SQL/TCP 5432;
> - Backend API → Redis, Generation Worker → Redis: RESP/TCP 6379;
> - Generation Worker → Claude API: HTTPS (Claude Messages API, JSON).
>
> **C-18 [MINOR] Напрям зв'язку Worker → Redis.** Стрілка від worker до Redis коректна (worker ініціює з'єднання і блокуюче отримання задачі); підпис «Отримує задачі» відповідає напряму. Зауваження відсутнє, зафіксовано для повноти.
>
> **C-19 [MAJOR] Зв'язок Recall → Claude API на Level 1.** Підпис «Генерує контент» не визначає, які дані залишають межу системи. Для приватності (SRS-FUN-25, Закон № 2297-VI) треба зафіксувати: передається текст лекцій і зразків, персональні дані студентів не передаються.
>
> **C-20 [MAJOR] Зв'язки акторів «Використовує».** Не визначено канал взаємодії (мобільний застосунок) і цілі (тестування, моніторинг). Рекомендація: підписи з основними сценаріями.
>
> ---
>
> ### 4. Пропозиції щодо відмовостійкості та безпеки (Комплаєнс 2026)
>
> **C-21 [BLOCKER] Reverse Proxy з TLS.** Додати контейнер Caddy або Nginx: термінація TLS 1.2+, проксування WebSocket, публікація лише 443. Закриває SRS-NFR-SEC-06.
>
> **C-22 [MAJOR] Сегментація мереж.** У docker-compose.yml один мережевий сегмент, PostgreSQL 5432 і Redis 6379 опубліковані на хост. Рекомендація: мережа edge (proxy, backend) і internal (backend, worker, PostgreSQL, Redis, без публікації портів).
>
> **C-23 [MAJOR] Секрети.** docker-compose.yml містить значення за замовчуванням `JWT_SECRET: dev-only-change-me` і передає ANTHROPIC_API_KEY у backend. Рекомендація: секрети через .env поза репозиторієм або Docker secrets; ANTHROPIC_API_KEY — лише в Generation Worker (принцип найменших привілеїв).
>
> **C-24 [MAJOR] Контроль вихідного трафіку.** Вихідний доступ до api.anthropic.com потрібен лише Generation Worker; Backend API зовнішніх викликів не виконує.
>
> **C-25 [MAJOR] Журналювання.** Рекомендовано зазначити на діаграмі спосіб збору журналів: JSON у stdout контейнерів (SRS-NFR-OBS-01), збір через `docker compose logs`. Для Enterprise-рівня рекомендовано централізований стек Loki + Grafana.
>
> **C-26 [MAJOR] Redis — єдина точка відмови черги.** Рекомендовано Redis Sentinel або Redis Cluster; мінімально — AOF persistence (SRS-NFR-REL-04).
>
> **C-27 [MAJOR] PostgreSQL — єдина точка відмови.** Рекомендовано потокову репліку і PgBouncer.
>
> **C-28 [MAJOR] Горизонтальне масштабування.** Рекомендовано оркестрацію Kubernetes з кількома репліками Backend API і Socket.io Redis adapter для розподілу кімнат між екземплярами.
>
> **C-29 [MAJOR] Контейнер резервного копіювання.** Додати Backup Job (pg_dump за розкладом cron) із записом на окремий носій. Закриває SRS-NFR-REL-03.
>
> **C-30 [MINOR] WAF / DDoS-захист.** Рекомендовано зовнішній WAF (Cloudflare) перед reverse proxy.
>

> **ЗВІТ АУДИТУ C4 Level 3 (Component Diagram) — Backend API «Recall»**
>
> Об'єкт аудиту: діаграма компонентів контейнера Backend API (Node.js 22, Express 5, Socket.io), перша версія.
> Базова лінія: docs/srs.md; діаграма контейнерів docs/2_design.md, підрозділ 2.1.2.
> Критерії: Clean Architecture (R. C. Martin) — правило залежностей; SOLID; GoF; DDD (bounded contexts модульного моноліту); OWASP ASVS 5.0, розділи V4 (Access Control), V5 (Validation), V7 (Error Handling and Logging).
> Позначення рівня: [BLOCKER] — порушення правила залежностей або вимоги безпеки SRS; [MAJOR] — відсутній компонент пайплайну, необхідний для SRS; [MINOR] — нотація.
>

>
> ### 1. Перевірка на порушення шарів
>
> **L-01 [BLOCKER] AttemptController → AttemptRepository.** Контролер шару Inbound звертається до репозиторію шару Outbound в обхід AttemptService. Порушено правило залежностей і SRP контролера; транзакційна межа «відповідь + ReviewState» (SRS-NFR-REL-01) стає неконтрольованою: запис може відбутися поза транзакцією сервісу. Рекомендація: контролери викликають лише сервіси.
>
> **L-02 [BLOCKER] Залежність Core → Outbound на конкретні класи.** AttemptService, SM2Scheduler, DailyPlanPrioritizer, AuthService залежать від конкретних репозиторіїв. Ядро залежить від деталей інфраструктури (pg, BullMQ) — порушення DIP і правила залежностей Clean Architecture. Рекомендація: інтерфейси (порти) у Core — `IAttemptRepository`, `IReviewStateRepository`, `IQuestionRepository`, `IUserRepository`, `IJobQueue`; реалізації в Outbound; зв'язування в Composition Root.
>
> **L-03 [MAJOR] SM2Scheduler → ReviewStateRepository.** Алгоритм SM-2 є чистою доменною функцією (вхід: ReviewState, q; вихід: новий ReviewState). Доступ до сховища всередині алгоритму змішує доменну логіку і I/O, ускладнює unit-тестування (SRS-NFR-MAINT-01). Рекомендація: SM2Scheduler без залежностей; читання і запис ReviewState виконує AttemptService у транзакції.
>
> **L-04 [MAJOR] ProgressPublisher → ProgressGateway.** Компонент Core залежить від компонента Inbound (Socket.io) — інверсія напряму залежностей. Рекомендація: ProgressPublisher публікує доменну подію через EventEmitter (Observer); ProgressGateway підписується на подію і транслює її в кімнату курсу.
>
> **L-05 [MAJOR] Відсутній Composition Root.** Не показано, де створюються і зв'язуються компоненти. Рекомендація: модуль `container` / `app.js`, що виконує Dependency Injection вручну (без DI-фреймворку) і є єдиним місцем знання про конкретні реалізації.
>
> **L-06 [MAJOR] Відсутня одиниця роботи (Unit of Work) / транзакційна межа.** SRS-NFR-REL-01 вимагає однієї ACID-транзакції для двох репозиторіїв; діаграма не визначає механізму передачі транзакції (спільний клієнт pg у межах `withTransaction`). Рекомендація: порт `ITransactionManager` у Core, реалізація в Outbound.
>
> ---
>
> ### 2. Аналіз патернів та SOLID
>
> **P-01 [MAJOR] SRP — AttemptService.** Сервіс поєднує видачу тесту, фіксацію відповіді, обчислення q, оркестрацію SM-2 і публікацію події. Рекомендація: QualityScorer (таблиця 2.1 SRS) — окремий чистий компонент; видача тесту — TestDeliveryService (рандомізація SRS-FUN-13, приховування правильних відповідей SRS-FUN-14, серверний таймер SRS-FUN-15).
>
> **P-02 [MAJOR] Відсутні компоненти для функціональних вимог SRS.** Не мають носія:
> - SRS-FUN-04…SRS-FUN-06 — коди запрошення, обмеження co-instructor (CourseService, InvitationService);
> - SRS-FUN-07…SRS-FUN-12 — курси, контрольні заходи, завантаження PDF, закриті зразки, журнал дій (CourseService, MaterialService, ContentAuditLog);
> - SRS-FUN-28, SRS-FUN-29 — модерація (ModerationService);
> - SRS-FUN-34…SRS-FUN-36 — пробний тест (MockTestService);
> - SRS-FUN-37…SRS-FUN-41 — приймання подій антисписування (AntiCheatEventService);
> - SRS-FUN-30 — ретрансляція подій задач (JobEventsListener на BullMQ QueueEvents);
> - SRS-FUN-46, SRS-FUN-47 — теплова карта і підтвердження (MasteryService);
> - SRS-FUN-48, SRS-FUN-49 — видалення даних (PrivacyService).
>
> **P-03 [MAJOR] OCP — типи контенту генерації.** GenerationJobService не визначає розширення для типів test, scenario, mock_test. Рекомендація: Strategy за типом контенту (валідація схеми, побудова промпту) — у Generation Worker; у Backend API — лише постановка задачі з типом.
>
> **P-04 [MINOR] ISP — репозиторії.** QuestionRepository обслуговує видачу тесту, пробний тест і модерацію. Рекомендація: розділити інтерфейси читання для студента (без правильних відповідей) і запису для модерації — це також конструктивно забезпечує SRS-FUN-14.
>
> **P-05 [MINOR] Патерни на зв'язках не підписано.** Рекомендація: підписи «DI», «interface call», «Observer / EventEmitter», «enqueue (BullMQ)», «SQL».
>
> **P-06 [MAJOR] DDD — межі модулів.** Компоненти не згруповано за bounded contexts модульного моноліту (identity, courses, testing, scheduling, generation, monitoring). Рекомендація: групування на діаграмі або колонка «Модуль» у таблиці; міжмодульні виклики — лише через публічні сервіси модуля.
>
> **P-07 [MAJOR] CQRS і окрема read-модель для дашборду.** Для Enterprise-рівня рекомендовано розділити команди і запити (CQRS) з окремою read-моделлю теплової карти, що оновлюється подіями.
>
> **P-08 [MAJOR] Event Sourcing для відповідей.** Рекомендовано зберігати відповіді як потік подій з відновленням ReviewState проєкцією.
>
> ---
>
> ### 3. Валідація повноти інженерного пайплайну
>
> **E-01 [BLOCKER] DTO Validation відсутня.** Немає компонента валідації вхідних даних на межі (тіло, параметри, query). OWASP ASVS V5; SRS-NFR-SEC-07 (обмеження файлу). Рекомендація: ValidationMiddleware на схемах zod для кожного маршруту; для завантаження — UploadMiddleware (multer, ліміт 10 МБ, MIME, сигнатура %PDF).
>
> **E-02 [BLOCKER] Global Error Handler відсутній.** Express 5 передає відхилені Promise в error-middleware, але без єдиного обробника клієнт отримує stack trace або різнотипні формати помилок. Рекомендація: ErrorHandler — єдиний формат (RFC 9457 Problem Details), відображення доменних помилок у коди 400 / 401 / 403 / 404 / 409 / 413 / 415 / 429, без розкриття внутрішніх деталей.
>
> **E-03 [MAJOR] Логування відсутнє.** SRS-NFR-OBS-01 вимагає JSON-журналів з requestId. Рекомендація: RequestContext (генерація requestId, AsyncLocalStorage) і Logger (pino); передача requestId у дані задачі BullMQ.
>
> **E-04 [MAJOR] Метрики відсутні.** Рекомендовано MetricsMiddleware (prom-client, гістограма тривалості запитів) з ендпоінтом /metrics для перевірки SRS-NFR-PERF-01 під час навантажувального тесту.
>
> **E-05 [MAJOR] Rate limiting відсутній.** SRS-NFR-SEC-08. Рекомендація: RateLimiter (express-rate-limit) з ключем userId для автентифікованих маршрутів і окремими лімітами для /auth/login (обліковий запис, IP).
>
> **E-06 [MAJOR] Healthcheck відсутній.** SRS-NFR-OBS-02: HealthController з перевіркою PostgreSQL і Redis.
>
> **E-07 [MAJOR] Ідемпотентність відповіді.** SRS-FUN-16: механізм не показано. Рекомендація: унікальне обмеження (attempt_id, question_id) у БД і обробка конфлікту в AttemptService.
>
> ---
>
> ### 4. Аудит безпеки на рівні коду сервісу
>
> **S-01 [BLOCKER] JWT Guard відсутній.** Немає компонента перевірки access-токена перед контролерами. Рекомендація: JwtAuthMiddleware (перевірка підпису, alg-allowlist, exp, issuer) для REST; аналогічна перевірка в handshake Socket.io (middleware `io.use`).
>
> **S-02 [BLOCKER] RBAC відсутній.** SRS-NFR-SEC-05, SRS-FUN-06, SRS-FUN-11, SRS-FUN-44: перевірка role_in_course не має компонента. Рекомендація: CourseRoleGuard — middleware з декларативною політикою маршруту (`requireCourseRole('owner')`, `requireCourseRole('owner','co-instructor')`), що читає Enrollment з репозиторію; та сама перевірка на `join` кімнати курсу в ProgressGateway.
>
> **S-03 [MAJOR] Ротація refresh-токенів.** SRS-NFR-SEC-02: AuthService не має сховища сімейств токенів. Рекомендація: RefreshTokenRepository (хеш токена, family_id, revoked_at) і логіка reuse detection в AuthService.
>
> **S-04 [MAJOR] Ліміт вартості LLM.** SRS-NFR-COST-02: постановка задачі не перевіряє добовий ліміт. Рекомендація: BudgetGuard у GenerationJobService із читанням агрегату generation_log.
>
> **S-05 [MAJOR] Захист від IDOR.** Перевірка ролі в курсі недостатня для ресурсів студента: студент того самого курсу не повинен отримувати спроби інших студентів. Рекомендація: перевірка власника ресурсу (ownership check) у сервісах для ролі student.
>
> **S-06 [MAJOR] Зовнішня авторизація політик.** Рекомендовано винести політики доступу в окремий Policy Decision Point (Open Policy Agent) для централізованого аудиту правил.
>
> **S-07 [MINOR] Заголовки безпеки.** Рекомендовано helmet для HTTP-заголовків (частина заголовків може встановлювати Caddy).
>
> **S-08 [MINOR] Обмеження CORS.** Мобільний клієнт не потребує CORS; middleware cors із довільним origin слід вимкнути або обмежити.
>
> ---
>

> 1. **Синхронний виклик Claude API в обробнику HTTP-запиту.** Найпростіша реалізація, але час відповіді дорівнює Latency провайдера.
> 2. **RabbitMQ (AMQP).** Повноцінний брокер повідомлень з підтвердженнями і dead-letter exchange.
> 3. **BullMQ на Redis.** Бібліотека черг для Node.js з повторними спробами, затримками і обмеженням паралелізму.
>
> ## Decision
>
> Обрано BullMQ на Redis 7 з окремим worker-процесом. Backend API ставить задачу в чергу і повертає 202 Accepted з ідентифікатором задачі. Worker виконує виклик Claude API, валідацію і збереження чернетки. Повторні спроби і dead-letter queue реалізуються засобами BullMQ.
>
> ## Consequences
>
> **Позитивні:**
> - Час відповіді API не залежить від Latency Claude API.
> - Повторні спроби і dead-letter queue без власної реалізації.
> - Redis уже присутній у стеку.
>
> **Негативні:**
> - Додатковий процес worker і сервіс Redis у docker-compose.
> - Потрібна доставка результату викладачу через WebSocket.

> ### 1. Критика аргументації (Decision Audit)
>
> **D-01 [BLOCKER] Рішення не виведено з критеріїв.** Розділ Decision констатує вибір, але не містить критеріїв вибору і їх ваг. Альтернативи не оцінено за однаковими критеріями. Рекомендація: матриця «критерій × альтернатива» з критеріями, що прямо відповідають SRS: Latency постановки (SRS-NFR-ASYNC-01), повторні спроби і DLQ (SRS-NFR-ASYNC-03), обмеження паралелізму (SRS-NFR-ASYNC-04), ідемпотентність (SRS-NFR-REL-02), стійкість стану черги (SRS-NFR-REL-04), кількість сервісів на супровід, операційна вартість.
>
> **D-02 [MAJOR] Кількісні межі в Context неповні.** «Від одиниць до десятків секунд» не є метрикою. Рекомендація: зафіксувати очікувану тривалість одного виклику (оцінка p95 ≤ 60 с, що відповідає timeout SRS-NFR-ASYNC-03) і наслідок для синхронного варіанта: p95 відповіді API ≥ Latency провайдера, тобто перевищення порогу 200 мс у сотні разів.

> **D-03 [MAJOR] Циклічний аргумент.** Позитивний наслідок «Redis уже присутній у стеку» не є незалежним аргументом: Redis присутній у стеку саме через BullMQ. Коректне формулювання: рішення не додає окремого брокера повідомлень; Redis 7 — єдиний додатковий сервіс інфраструктури черги.
>
> **D-04 [MAJOR] Відсутній зв'язок з бюджетом і моделлю провайдера.** Рішення про чергу визначає точку контролю витрат (worker — єдиний споживач Claude API), але це не зафіксовано. SRS-NFR-COST-01, SRS-NFR-COST-02 не згадано.

> **D-05 [MAJOR] Відсутній опис взаємодії з механізмом повторних спроб SDK.** Офіційний SDK Anthropic за замовчуванням виконує 2 повторні спроби для 408 / 409 / 429 / 5xx. > ### 2. Аналіз альтернатив
>
> **A-01 [MAJOR] Синхронний виклик описано неповно.** Не зазначено конкретних наслідків: блокування з'єднання на час виклику, обрив запиту мобільним клієнтом при зміні мережі, повторне надсилання запиту клієнтом і подвійна тарифікація, неможливість обмежити паралелізм на рівні системи (кожен викладач ініціює власний виклик), відсутність DLQ. Варіант порушує SRS-NFR-ASYNC-01 за визначенням.
>
> **A-02 [MAJOR] RabbitMQ описано без компромісів.** Не наведено: окремий сервіс з власною конфігурацією (exchanges, queues, bindings, policies), окремий клієнт amqplib без вбудованої семантики задач, власна реалізація exponential backoff (через TTL + dead-letter exchange або плагін delayed message exchange), окремий моніторинг. Переваги RabbitMQ (підтвердження доставки, маршрутизація, quorum queues, кластеризація) не відповідають жодній вимозі SRS при одному типі споживача і одному хості.
>
> **A-03 [MAJOR] Відсутні альтернативи, що є стандартними для цього класу задач:**
> - **PostgreSQL як черга** (pg-boss / graphile-worker, `SELECT … FOR UPDATE SKIP LOCKED`): не потребує Redis, транзакційна постановка задачі разом із записом у БД (outbox без окремого механізму), PostgreSQL уже є джерелом істини.
> - **Вбудований фоновий виконавець у процесі API** (in-process queue, `setImmediate` / p-queue): відсутність окремого сервісу; втрата задач при перезапуску процесу.
> - **Message Batches API провайдера**: знижена вартість обробки при асинхронному виконанні з часом завершення до 24 год.
> - **Керовані черги хмарних провайдерів** (Amazon SQS, Google Cloud Tasks).
>
> **A-04 [MAJOR] Відсутнє обґрунтування відхилення PostgreSQL-черги.** Для системи з PostgreSQL як джерелом істини черга на PostgreSQL — найближча альтернатива за складністю. Відхилення потребує аргументу: навантаження polling на БД, що обслуговує SRS-NFR-PERF-01/02; відсутність вбудованого QueueEvents для SRS-FUN-30; відсутність обмеження паралелізму на рівні черги у pg-boss без додаткової конфігурації. Аргументи треба зафіксувати або змінити рішення.
>
> **A-05 [MINOR] Message Batches API.** Час завершення пакета до 24 год несумісний із SRS-NFR-ASYNC-02 (p95 ≤ 90 с); альтернативу слід навести і відхилити з цим аргументом, оскільки вона є першим кандидатом при оптимізації вартості.
>
> **A-06 [MINOR] Керовані хмарні черги.** Несумісні з обмеженням «розгортання на одному хості без хмарного бюджету»; навести і відхилити.
>

> ### 3. Аудит наслідків (Consequences Trade-off)
>
> **C-01 [BLOCKER] Redis — єдина точка відмови черги.** Не зазначено: при недоступності Redis постановка задач неможлива (Backend API повертає помилку замість 202), обробка зупиняється, QueueEvents не доставляються. Рекомендація: явний негативний наслідок, поведінка API (503 з Retry-After), healthcheck (SRS-NFR-OBS-02), відновлення через AOF (SRS-NFR-REL-04).
>
> **C-02 [BLOCKER] Семантика доставки at-least-once.** BullMQ гарантує щонайменше одну обробку: задача, worker якої завершився аварійно після виклику Claude API, але до підтвердження, обробляється повторно (stalled job). Наслідки: дублікат чернетки і повторна тарифікація. Рекомендація: ідемпотентність за jobId (SRS-NFR-REL-02) і унікальне обмеження чернетки за jobId у PostgreSQL; повторна тарифікація — прийнятий ризик з оцінкою.
>
> **C-03 [MAJOR] Персистентність Redis.** Без AOF перезапуск контейнера Redis втрачає задачі в черзі. Рекомендація: appendonly yes, appendfsync everysec — втрата до 1 с записів; наслідок: навантаження на диск і розмір файлу AOF.
>
> **C-04 [MAJOR] Розбіжність стану між Redis і PostgreSQL.** Задача в Redis і запис GenerationJob у PostgreSQL можуть розійтися (постановка в чергу виконалась, транзакція в БД — ні, або навпаки). Рекомендація: порядок операцій — запис GenerationJob у PostgreSQL зі статусом queued, потім enqueue з jobId; узгодження зависших записів при старті worker. Альтернатива — transactional outbox; для MVP достатньо узгодження.
>
> **C-05 [MAJOR] Ускладнення тестування.** Не зазначено: інтеграційні тести потребують Redis у контейнері, керованої заглушки Claude API (nock) і очікування стану задачі; час тестів у CI зростає; тести з реальними затримками backoff (5 с, 10 с) потребують налаштування затримок через конфігурацію.
>
> **C-06 [MAJOR] FinOps.** Не оцінено вартість: worker — єдиний споживач Claude API, тому вартість контролюється в одній точці (SRS-NFR-COST-01, SRS-NFR-COST-02). Повторні спроби множать вартість невдалих задач (до 3 викликів). Рекомендація: оцінка вартості задачі в токенах і USD для обраної моделі; ліміт max_tokens; добовий ліміт; облік у generation_log.
>
> **C-07 [MAJOR] Затримка для користувача не зникає.** Асинхронність переносить очікування з HTTP-з'єднання на інтерфейс: викладач отримує результат через 10–90 с. Потрібен UX стану задачі і доставка події завершення (SRS-FUN-30) — наслідок, що створює залежність від каналу WebSocket.
>
> **C-08 [MAJOR] Відсутні умови перегляду рішення.** ADR не визначає тригерів перегляду: зростання кількості споживачів понад один тип, вимога гарантій exactly-once, вимога горизонтального масштабування worker на кількох хостах, вартість Redis як окремого сервісу.
>
> **C-09 [MAJOR] Високодоступна конфігурація Redis.** Для Enterprise-рівня 2026 року рекомендовано Redis Sentinel або керований Redis (Amazon ElastiCache, Upstash) для усунення єдиної точки відмови.
>
> **C-10 [MINOR] Status.** Рішення використовується як база діаграм C4 Level 2–3, тоді як ADR має статус Proposed. Рекомендація: після рецензії — Approved (Accepted) з датою.
>

> **Підсумок.** 3 BLOCKER (D-01, C-01, C-02), 15 MAJOR, 4 MINOR. Рішення технічно прийнятне для обмежень проєкту, але в поточному вигляді не обґрунтоване метриками, не розглядає найближчу альтернативу (черга на PostgreSQL) і не фіксує негативних наслідків семантики at-least-once та єдиної точки відмови.
