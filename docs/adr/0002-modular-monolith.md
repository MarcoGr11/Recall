# ADR-002. Архітектурний стиль серверної частини: модульний моноліт за Ports and Adapters

**Status:** Approved
**Date:** 24.11.2026
**Автор рішення:** MarcoGr11
**Пов'язані артефакти:** [srs.md](../srs.md), [2_design.md](../2_design.md) — підрозділи 2.1.1, 2.2.2, 2.3; [ADR-001](0001-choice-of-technology.md)

## Context

Серверна частина Recall обслуговує мобільний клієнт студента і викладача: REST API, канал Socket.io для моніторингу в реальному часі, планування повторення за SM-2 і асинхронну генерацію контенту через Claude API (ADR-001). Стиль серверної частини визначає, як виконуються вимоги, наведені в таблиці 1.

Таблиця 1 – Вимоги, що визначають архітектурний стиль

| Вимога | Метрика | Що вимагає від стилю |
|---|---|---|
| [SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01) | Результати спроби і ReviewState — в одній ACID-транзакції | Атомарний запис у таблиці двох предметних областей (тестування і планування) |
| [SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01), [SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02) | p95 ≤ 300 мс (читання) і ≤ 500 мс (запис відповіді, завершення спроби) при 50 RPS | Мінімум мережевих переходів у шляху запиту |
| [SRS-NFR-RT-01](../srs.md#srs-nfr-rt-01) | Подія прогресу p95 ≤ 1 с від commit до панелі викладача, 100 з'єднань | Доставка події без проміжного брокера |
| [SRS-NFR-MAINT-01](../srs.md#srs-nfr-maint-01) | ≥ 70 % рядків і гілок для SM-2 і пріоритизації плану | Доменна логіка тестується без PostgreSQL, Express і Redis |
| [SRS-NFR-SEC-05](../srs.md#srs-nfr-sec-05) | Перевірка role_in_course на сервері для кожного запиту | Єдина точка контролю доступу |
| [SRS-NFR-INFRA-01](../srs.md#srs-nfr-infra-01) | docker-compose на одному хості | Кількість процесів і контейнерів, що вміщується в 4 vCPU і 8 ГБ RAM |

Обмеження проєкту: соло-розробка тривалістю 6 місяців; один хост docker-compose (4 vCPU, 8 ГБ RAM); один потік до 100 студентів; хмарний бюджет відсутній; персональні дані студентів не передаються стороннім сервісам, крім листів через SMTP-провайдера і тексту лекцій у Claude API.

## Alternatives

### 1. Шаровий моноліт (Controller → Service → DAO)

Один процес Express; сервіси напряму використовують Kysely і BullMQ. Виконує SRS-NFR-REL-01 і SRS-NFR-PERF-01 без додаткових механізмів. Недолік: доменна логіка SM-2 і пріоритизації залежить від драйвера бази даних, тому кожен тест критичних модулів потребує PostgreSQL; Generation Worker не може повторно використати сервіси без транзитивної залежності від Express.

### 2. Модульний моноліт за Ports and Adapters

Одна кодова база, поділена на модулі предметної області; усередині модуля — шари Inbound, Core, Ports, Outbound з інверсією залежностей; два процеси з однієї кодової бази (Backend API і Generation Worker, ADR-001); одна схема PostgreSQL, таблиці закріплено за модулями-власниками. Виконує REL-01 однією транзакцією, PERF і RT-01 — викликами в межах процесу, MAINT-01 — тестуванням Core з підробками портів.

### 3. Мікросервіси

Окремі сервіси identity, courses, testing, scheduling, generation, monitoring з базою даних на сервіс і брокером подій. Завершення спроби змінює дані testing і scheduling, тому SRS-NFR-REL-01 потребує Saga з компенсувальними діями: ReviewState стає узгодженим лише в кінцевому підсумку (Eventual Consistency), що суперечить вимозі ACID-транзакції. Кожен запит з перевіркою ролі додає мережевий виклик до сервісу courses. Шість сервісів, шість баз або схем і брокер на одному хості 4 vCPU — щонайменше 13 контейнерів замість 7.

### 4. Backend as a Service (Supabase)

Автентифікація, PostgreSQL з Row Level Security і Realtime надає провайдер; доменна логіка — у функціях Edge Functions. Транзакція завершення спроби і серверний таймер реалізуються функціями PostgreSQL або Edge Functions, тобто логіка SM-2 розщеплюється між SQL і TypeScript у середовищі Deno. Персональні дані і журнали антисписування зберігаються в хмарі провайдера; безкоштовний тариф обмежує кількість з'єднань Realtime і призупиняє неактивні проєкти, а хмарний бюджет відсутній.

### Відхилені без детального аналізу

- Serverless-функції (AWS Lambda): холодний старт суперечить SRS-NFR-PERF-01, кімнати Socket.io потребують постійного процесу.
- Моноліт без окремого процесу worker: розглянуто в ADR-001 (альтернатива 2), відхилено.

## Decision

Серверна частина реалізується як модульний моноліт з архітектурою Ports and Adapters (варіант Clean Architecture) усередині модулів:
1. Вісім модулів: identity, courses, testing, scheduling, generation, monitoring, privacy, platform. Кожна таблиця схеми даних має один модуль-власник; запис у таблицю виконують лише порти модуля-власника. Модуль звертається до іншого модуля лише через його публічні сервіси Core. Єдиний виняток — транзакція завершення спроби: AttemptService (testing) записує ReviewState через порт модуля scheduling в одній транзакції (SRS-NFR-REL-01).
2. Правило залежностей Inbound → Core → Ports ← Outbound і правило меж модулів перевіряються в CI статичним аналізом імпортів (dependency-cruiser), оскільки сервер написано на JavaScript без статичних типів.
3. Два процеси з однієї кодової бази: Backend API і Generation Worker (ADR-001). Кожен процес має власний корінь композиції (`api.js`, `worker.js`), обидва збирають сервіси Core однією фабрикою `createCore()`.
4. Backend API працює в одному екземплярі; масштабування — вертикальне, у межах ресурсів хоста.

## Consequences

### Позитивні

- SRS-NFR-REL-01 виконується однією транзакцією PostgreSQL без Saga і компенсувальних дій.
- Виклики між модулями — виклики функцій у межах процесу; мережеві переходи в шляху запиту: Reverse Proxy → Backend API → PostgreSQL.
- Подія прогресу доставляється в межах процесу без брокера (SRS-NFR-RT-01).
- QualityScorer, SM2Scheduler і PlanAllocator — чисті функції; покриття SRS-NFR-MAINT-01 досягається unit-тестами без контейнерів.
- Один образ контейнера для Backend API і Generation Worker, що відрізняються командою запуску.

### Негативні

- **Спільна схема даних.** Модулі не розгортаються незалежно; винесення модуля в окремий сервіс потребує розділення схеми і не є метою проєкту.
- **Один екземпляр Backend API.** Шина подій ProgressPublisher (EventEmitter), лічильники rate limiting і кімнати Socket.io зберігаються в пам'яті процесу. Другий екземпляр потребує адаптера Socket.io для Redis, сховища лічильників у Redis і доставки доменних подій між процесами.
- **Хост — єдина точка відмови.** Доступність обмежена доступністю одного хоста; відновлення — з резервної копії за SRS-NFR-REL-03. Прийнятий ризик для апробації в одному потоці.
- **Спільні ресурси процесору.** Argon2id, вилучення тексту PDF і обробка запитів конкурують за 4 vCPU; потрібні обмеження ресурсів контейнерів і винесення CPU-важких операцій з event loop.
- **Відсутність статичних типів.** Інтерфейси портів — це контракти, описані JSDoc; їх дотримання перевіряють тести і dependency-cruiser, а не компілятор.

### Умови перегляду рішення

- p95 SRS-NFR-PERF-01 перевищено при 50 RPS після вичерпання вертикального масштабування хоста;
- система обслуговує більше одного закладу або потоку з вимогою доступності, вищою за доступність одного хоста;
- над окремими модулями працюють різні команди.
