# Killer feature та ключовий функціонал

> Оновлено після зміни теми (сесія/навчальний рік замість БЗВП). Killer feature — одна (сценарії); решта нижче — важливий функціонал продукту, але не рівня унікальності "такого ще нема на ринку".

## Killer feature: сценарний тренажер рішень з AI-генерацією чернеток

Замість лінійних тестів — інтерактивний сценарій з розгалуженнями на матеріалі реальних інженерних кейсів (наприклад: "продакшн впав о 3 ночі — що робити першим", "конфлікт при мерджі гілок — як вирішити", архітектурна задача з наслідками кожного рішення). Студент на кожному кроці обирає дію, вибір веде до наступного кроку; в кінці — розбір усього шляху з поясненням, де і чому сталась помилка.

### Конвеєр генерації та курації контенту

1. Викладач вручну ініціює генерацію: обирає предмет ([[07-Навчальні модулі]]), тему, рівень складності
2. Backend кладе завдання в чергу (Redis + BullMQ), воркер асинхронно викликає Claude API (Haiku 4.5), записує чернетку зі статусом `draft`
3. Викладач бачить чернетку в черзі модерації — схвалює / редагує / відхиляє
4. Тільки після підтвердження сценарій стає доступний студентам

## Функціонал: персональний план підготовки на день

Розвиток інтеграції з розкладом сесії. Система щодня розраховує пріоритет для кожної теми/предмету = функція від (днів до іспиту, слабкість теми за SM-2, тривалість неповторення) і видає студенту короткий список: "сьогодні: 40 хв [Предмет], 20 хв [Предмет]".

Нова таблиця:
```
exam_schedule: id, course_id, exam_date, weight
```


## Функціонал: дерево знань (візуалізація прогалин)

Візуалізація у вигляді дерева, а не матриці: **стовбур** — флагманський модуль (evergreen-теми, спільний для всіх незалежно від викладача), **гілки** — окремі курси різних викладачів, **листки** — теми/тести в межах гілки чи стовбура.

Колір листка визначається `mastery_score`, розрахованим з `sm2_progress.ease_factor` (нормалізація в діапазон 0–100%):

```
mastery_score = clamp((ease_factor - 1.3) / (2.5 - 1.3) * 100, 0, 100)
```

| Колір | Діапазон mastery_score |
|---|---|
| 🟢 Зелений | 85–100% |
| 🟡 Жовтий | 60–84% |
| 🟠 Оранжевий | 35–59% |
| 🔴 Червоний | 0–34% |

Листок не фіксується назавжди — колір оновлюється автоматично при кожному перерахунку SM-2 після нової спроби (тобто відображає накопичений прогрес, а не лише останній тест).

Доступна і студенту (власне дерево), і викладачу (дерево по всій групі — тільки гілка свого курсу + спільний стовбур).

Не потребує нової таблиці для самого дерева — агрегуючий запит над `sm2_progress` і `topics` (`course_id IS NULL` → стовбур, `course_id = X` → гілка курсу X).

### Пул провалених питань (доповнення до SM-2)

Окремий, доповнюючий механізм на рівні **питань**, а не тем: провалені питання конкретного тесту підмішуються як додаткові в наступний тест з цієї ж теми, поки студент не дасть правильну відповідь.

```
question_attempts: id, user_id, question_id, test_attempt_id, is_correct, answered_at
```

Логіка формування наступного тесту: нові/ротаційні питання з теми + питання з `question_attempts`, де `is_correct = false` і ще немає підтвердженої правильної повторної відповіді.

## Флагманський навчальний модуль: Основи інженерії ПЗ

Повний перелік тем і пріоритет анімації — [[07-Навчальні модулі]]. Ключова технічна відмінність від предметних тем: немає дати іспиту, тому звичайна SM-2-пріоритизація за розкладом сесії тут не застосовується.

### Механіка повторення (evergreen, як у Duolingo/Anki)

- `topics.module_type`: `'exam'` (звичайні предметні теми, пріоритет росте до дати іспиту) або `'evergreen'` (флагманський модуль, пріоритет постійний, без дедлайну)
- Стрік (streak): лічильник послідовних днів практики — `user_streaks: user_id, topic_id, current_streak, longest_streak, last_practiced_date`. Пропуск дня обнуляє стрік — це і мотивує повертатись щодня
- У щоденному персональному плані завжди є мінімальна гарантована порція evergreen-теми (наприклад, 5-10 хв), незалежно від того, скільки предметних тем "горить" перед сесією

## Функціонал: AI-генерація тестів з лекційних матеріалів

**Типовий сценарій використання**: один предмет — приблизно 15 лекцій. Викладач завантажує лекцію (PDF/текст), яка стає окремою темою курсу; система парсить вміст і через **той самий узагальнений конвеєр генерації**, що й сценарії (черга Redis+BullMQ → Claude API → модерація → публікація), формує чернетку тесту з питаннями, варіантами відповідей і поясненнями. Це не нова окрема підсистема, а друге застосування вже спроєктованої архітектури — інший тип вхідних даних (текст лекції замість параметрів сценарію) і інший тип контенту на виході (тест замість дерева рішень).

Дата екзамену/заліку для курсу — **орієнтовна** (вказує викладач, достатньо приблизно "через N тижнів", а не точна дата з офіційного розкладу) — цього достатньо для SM-2-пріоритизації і знімає залежність від того, коли вищий заклад затвердить офіційний розклад сесії.

### Конвеєр

1. Викладач завантажує файл лекції, прив'язує до предмету/теми
2. Backend парсить текст (PDF → `pdf-parse`), розбиває на змістові шматки
3. Завдання на генерацію летить у чергу, воркер викликає Claude API з текстом лекції як контекстом
4. Чернетка тесту потрапляє в ту саму чергу модерації — викладач схвалює / редагує / відхиляє
5. Тільки після підтвердження тест стає доступний студентам

### Обмеження MVP

- Тільки PDF і звичайний текст (docx/pptx — перспектива розвитку)
- Один файл = одна тема, прив'язка вручну викладачем
- Ліміт розміру файлу для контролю вартості генерації
