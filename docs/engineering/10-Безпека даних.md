# Безпека даних

## Шифрування

- Дані під час передачі — HTTPS, WSS для real-time з'єднання викладач-студент
- Дані на сервері (at rest) — шифрування чутливих полів БД
- Дані на пристрої — локальне шифрування SQLite (SQLCipher), якщо офлайн-режим залишається (див. [[09-Технічний стек#Офлайн-режим (під питанням)]])

## Авторизація і розмежування доступу

- JWT-токени з обмеженим терміном дії + refresh token
- Middleware-перевірка на кожному API-запиті: студент бачить тільки своє, викладач — тільки свій курс (див. [[06-Ролі та архітектура]])

## Мінімізація даних

- Зберігати лише необхідне, можливість використання ID/псевдоніма замість повного ПІБ
- Завантажені лекційні матеріали доступні лише учасникам конкретного курсу, не публічно

## Аудит дій

- Логування: хто і коли підтвердив тест чи сценарій, хто змінював склад курсу, хто завантажив лекційний матеріал

## Захист від несанкціонованого доступу

- Rate limiting на API
- Валідація вхідних даних на backend, не тільки на клієнті
- Валідація типу й розміру файлу при завантаженні лекцій (захист від зловмисних файлів, DoS через великі файли)

## Юридичний аспект

- Закон України "Про захист персональних даних"
- Авторське право на лекційні матеріали — завантажує сам викладач-автор, тому конфлікту прав не виникає; матеріали не поширюються за межі курсу
- Питання: чи потрібна формальна згода учасників апробації (одногрупників), якщо збиратимемо їхні реальні дані для експериментальної частини диплому — уточнити в керівника

## Додатково враховані практичні моменти

- Резервне копіювання даних сервера
- Реєстрація за номером телефону, без обов'язкового email
- Коректна робота на слабших/старіших Android-пристроях
- Модель використання: один пристрій — один студент — один акаунт (спільні пристрої не підтримуються)
- Енергоефективність анімацій і фонового WebSocket-з'єднання
- Рандомізація порядку питань і відповідей у тестах — захист від списування
