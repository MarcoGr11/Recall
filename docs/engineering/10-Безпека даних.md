# Безпека даних

## Шифрування

- Дані під час передачі — HTTPS, WSS для real-time з'єднання викладач-студент
- Дані на сервері (at rest) — поля БД на рівні застосунку не шифруються (оновлено 24.11.2026, підрозділ 2.4 [2_design.md](../2_design.md)): паролі, refresh-токени й одноразові токени зберігаються лише як хеші; резервні копії шифруються утилітою `age`
- Дані на пристрої — токени лише в expo-secure-store з класом доступності `WHEN_UNLOCKED_THIS_DEVICE_ONLY` ([SRS-NFR-SEC-04](../srs.md#srs-nfr-sec-04)); локальна база даних із шифруванням не використовується
- SMTP-з'єднання з `requireTLS: true`; домен відправника має записи SPF, DKIM і DMARC

## Автентифікація і відновлення доступу

Рішення автора від 24.11.2026: вхід за корпоративною поштою закладу і паролем, номер телефону не використовується ([SRS-FUN-01](../srs.md#srs-fun-01), [SRS-FUN-02](../srs.md#srs-fun-02), [SRS-FUN-55](../srs.md#srs-fun-55)).

- Реєстрація лише з пошти домену з переліку дозволених (змінна конфігурації `ALLOWED_EMAIL_DOMAINS`, за замовчуванням `chnu.edu.ua`); інший домен → 422; пошта порівнюється без урахування регістру (`citext`)
- Пароль 10–128 символів після нормалізації NFKC, хеш Argon2id (бібліотека `argon2`, m = 19 456 KiB, t = 2, p = 1) з повторним хешуванням застарілих параметрів під час входу; пароль з переліку 100 000 поширених → 422; не більше 4 обчислень Argon2id одночасно, черга до 50, далі 503
- Access-токен JWT: лише HS256, обов'язкові claims `sub`, `iss`, `aud`, `iat`, `exp`, розходження годинників ≤ 30 с; секрет ≥ 32 байти з Docker secrets, ротація через `kid`; refresh-сімейство живе не довше 30 днів від входу, ротація — під `SELECT … FOR UPDATE`
- Невдалі входи: 5/хв на пару «адреса + IP» і 100/год на адресу, у тому числі для незареєстрованих адрес (власника облікового запису не блокує атакувальник з іншої IP-адреси)
- Запит з чинним access-токеном видаленого облікового запису → 401
- Реєстрація не розкриває існування облікового запису (user enumeration, OWASP A07:2021): відповідь завжди 202, для вже зареєстрованої адреси обліковий запис не змінюється, а на адресу надходить лист «обліковий запис уже існує» з посиланням на відновлення пароля; лист надсилається після відповіді
- Підтвердження пошти одноразовим посиланням (строк дії 24 год) перед першим входом; вхід з правильним паролем до підтвердження → 403, невірний пароль → 401 незалежно від стану пошти; для відсутньої адреси хешується фіктивний пароль, щоб час відповіді не розкривав існування облікового запису
- Відновлення пароля одноразовим токеном у посиланні на пошту: у БД зберігається лише хеш SHA-256 (`password_reset_tokens`), строк дії 30 хв, повторне використання відхиляється; після встановлення нового пароля відкликаються всі refresh-токени користувача
- Відповідь на запит відновлення завжди 202, незалежно від існування адреси (захист від перебору облікових записів, user enumeration); лист надсилається після відповіді, тому час відповіді теж не залежить від існування адреси; новий запит анулює попередні невикористані токени
- Посилання з листа — universal link (Android App Links, iOS Universal Links) на екран нового пароля або підтвердження пошти в застосунку; токен передається у фрагменті URL (`#token=…`), який не надсилається на сервер і не потрапляє в журнали та `Referer`; на комп'ютері статична сторінка з `Referrer-Policy: no-referrer` просить відкрити лист на телефоні (UC-03, підрозділ 2.6 [2_design.md](../2_design.md))
- Rate limit на запит відновлення і повторний лист підтвердження: 5 запитів/год на поштову адресу і 5 запитів/год на IP; реєстрація: 5 запитів/год на адресу і 60 запитів/год на IP (60, а не менше, оскільки студенти групи реєструються з однієї IP-адреси NAT аудиторії); підтвердження пошти і встановлення нового пароля: 60 запитів/год на IP; оновлення токенів: 120 запитів/хв на IP; перевищення → 429 з Retry-After
- IP клієнта визначається з `X-Forwarded-For`, який встановлює Reverse Proxy; Express довіряє лише одному проміжному вузлу (`trust proxy` = 1), тому підроблений клієнтом заголовок ліміт не обходить; ліміт на користувача рахується за `sub` уже перевіреного access-токена
- Видалення облікового запису (`POST /me/deletion`) вимагає поточного пароля: викрадений access-токен не дає змоги незворотно видалити обліковий запис
- Листи надсилає адаптер SmtpMailSender через SMTP-провайдера (порт 587, STARTTLS) після відповіді клієнту, тайм-аут з'єднання 10 с, збій журналюється, користувач повторює запит; у dev/test — ConsoleMailSender записує лист у журнал; при `NODE_ENV=production` і `MAIL_TRANSPORT` ≠ `smtp` сервер не запускається, щоб одноразові токени не потрапили в журнали
- Мобільний клієнт виконує не більше одного оновлення токенів одночасно (паралельні запити очікують результату одного `/auth/refresh`), тому reuse detection не відкликає сесію через гонку запитів
- Socket.io: роль перевіряється під час приєднання до кімнати, вилучений учасник негайно виключається з кімнати; строк дії access-токена перевіряється на кожній події, після закінчення — подія `auth.expired` і розрив з'єднання; не більше 60 подій клієнта за хвилину на з'єднання (оновлено 24.11.2026, підрозділ 2.1.1 [2_design.md](../2_design.md))

## Авторизація і розмежування доступу

- JWT-токени з обмеженим терміном дії + refresh token
- Middleware-перевірка на кожному API-запиті: студент бачить тільки своє, викладач — тільки свій курс (див. [[06-Ролі та архітектура]])
- Захист від BOLA для вкладених ідентифікаторів: тема, контрольний захід, матеріал, зразок, питання і учасник у шляху або тілі мають належати курсу зі шляху, питання — спробі; інакше 404, щоб не розкривати існування чужого UUID (підрозділ 2.5 [2_design.md](../2_design.md))

## Мінімізація даних

- Зберігати лише необхідне, можливість використання ID/псевдоніма замість повного ПІБ
- Номер телефону не збирається: ідентифікатор облікового запису — корпоративна пошта закладу
- Завантажені лекційні матеріали доступні лише учасникам конкретного курсу, не публічно

## Аудит дій

- Логування: хто і коли підтвердив тест чи сценарій, хто змінював склад курсу, хто завантажив лекційний матеріал
- Події безпеки в `audit_log`: зміна пароля, повторне використання refresh-токена (AuthService), зміна і вилучення ролей (CourseService), видалення облікового запису (PrivacyService); невдалі входи і відповіді 401, 403, 404, 429 — у журналі pino; сповіщення поза MVP, журнали переглядаються вручну

## Захист від несанкціонованого доступу

- Rate limiting на API: окремо за IP (усі маршрути і окремо публічні операції) і за користувачем (100 запитів/хв, 20 завантажень PDF/год)
- Журнали не містять секретів: pino приховує заголовок Authorization і поля password, newPassword, refreshToken, token, code, поштова адреса маскується; журнал доступу Reverse Proxy пише шлях без query-рядка
- Ліміт тіла запиту: Reverse Proxy — 11 МБ, Backend API — JSON 100 КБ, файл 10 МБ (413); невідповідний Content-Type → 415
- CORS middleware не підключено: браузерного клієнта немає, крос-доменні запити з браузера блокуються; Socket.io — `cors: false`, токен на handshake лише в полі `auth`
- Валідація вхідних даних на backend, не тільки на клієнті: zod у режимі `.strict()` (невідоме поле → 400), помилки без вхідних значень; репозиторії записують поля явно, відповіді формують вихідні DTO (захист від Mass Assignment і надлишкового розкриття даних)
- Глобальний ліміт 300 запитів/хв на IP для всіх маршрутів до розбору тіла; лічильники лімітів у Redis
- PDF: pdfjs-dist ≥ 4.2.67 з `isEvalSupported: false`, `resourceLimits` 256 МБ на потік, ім'я файлу — серверний UUID
- Відповідність OWASP Top 10:2021 і API Security Top 10:2023 — таблиця підрозділу 2.4 [2_design.md](../2_design.md)
- Валідація типу й розміру файлу при завантаженні лекцій (захист від зловмисних файлів, DoS через великі файли)

## Юридичний аспект

- Закон України "Про захист персональних даних"
- Авторське право на лекційні матеріали — завантажує сам викладач-автор, тому конфлікту прав не виникає; матеріали не поширюються за межі курсу
- Питання: чи потрібна формальна згода учасників апробації (одногрупників), якщо збиратимемо їхні реальні дані для експериментальної частини диплому — уточнити в керівника

## Додатково враховані практичні моменти

- Резервне копіювання даних сервера
- Реєстрація за корпоративною поштою закладу (домен з переліку дозволених), без номера телефону
- Коректна робота на слабших/старіших Android-пристроях
- Модель використання: один пристрій — один студент — один акаунт (спільні пристрої не підтримуються)
- Енергоефективність анімацій і фонового WebSocket-з'єднання
- Рандомізація порядку питань і відповідей у тестах — захист від списування
