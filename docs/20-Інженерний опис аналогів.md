# Інженерний опис аналогів

Інженерний аналіз трьох аналогів платформи Recall (Moodle, Anki, Quizlet) для підрозділу 1.2 пояснювальної записки. Предмет аналізу — програмна система: архітектура, протоколи, зберігання даних, обмеження. Інтерфейс, вартість і поширеність не розглядаються.

Попередній продуктовий огляд: [[12-Аналіз аналогів]]. Зведена таблиця: [[21-Порівняльна матриця аналогів]].

> [!info] Позначення
> Для закритих систем твердження без офіційного джерела позначено як «імовірно» (архітектурне припущення) або «за публічно доступними даними» (джерело є, але застаріле чи непряме).

## 1. Moodle

### 1.1 Архітектурний патерн і вплив на масштабованість

Moodle — серверний монолітний вебзастосунок на PHP з плагінною архітектурою: функціональність (модулі активностей, блоки, методи автентифікації, web service протоколи) підключається як плагіни стандартизованих типів у межах одного процесу та однієї кодової бази.

Горизонтальне масштабування здійснюється кластеризацією ідентичних вузлів за балансувальником навантаження. Офіційна документація встановлює обов'язкові умови кластера:
- спільний каталог `dataroot` (moodledata), до якого всі вузли звертаються безпосередньо;
- централізоване сховище сесій (рекомендовано Redis);
- спільне сховище для кешів MUC (Moodle Universal Cache) — Redis або Memcached; `localcachedir` може бути локальним для кожного вузла;
- один спільний ACID-сумісний сервер БД.

Отже, вебвузли є взаємозамінними, а стан зосереджено у трьох спільних компонентах (БД, файлове сховище, кеш/сесії), які обмежують масштабування.

Фонова обробка виконується через Task API: scheduled tasks (за розкладом) та ad-hoc tasks (черга разових задач). Задачі запускаються процесом cron, частоту якого рекомендовано встановлювати не рідше одного разу на хвилину; задачі не можуть виконуватися частіше, ніж запускається cron. Невдалі задачі повторюються з наростаючою затримкою від 1 хвилини до 24 годин; для ad-hoc tasks з версії 4.4 за замовчуванням передбачено 12 повторних спроб.

### 1.2 Протоколи передачі даних і взаємодії

- **HTTP/HTTPS, серверний рендеринг** — основний канал вебінтерфейсу.
- **AJAX через External API** — вебінтерфейс та офіційний мобільний застосунок використовують ті самі external functions, що й зовнішні інтеграції.
- **Web services**: у ядрі доступні протоколи REST і SOAP. Протокол XML-RPC вилучено з ядра у версії 4.1 (MDL-76052) і перенесено в окремий плагін через вилучення розширення php-xmlrpc з PHP 8.0.
- **Real-time канал**: у ядрі WebSocket-транспорт не передбачено. Двонаправлену доставку подій реалізує сторонній плагін `tool_realtime`: за замовчуванням через PHP polling, опційно через WebSocket-сервер Centrifugo.

### 1.3 Стек даних і механізми консистентності

- **Реляційна СУБД** через рівень абстракції DML; підтримувані платформи — PostgreSQL, MySQL, MariaDB, Microsoft SQL Server. Підтримку Oracle припинено з версії 5.0.
- **Транзакції**: механізм delegated transactions з вкладеністю, де зовнішній рівень керує внутрішніми; позначення транзакції на rollback на будь-якому рівні є незворотним, а незбалансовані транзакції спричиняють `transaction_exception` і rollback.
- **Файли** — у `dataroot` або альтернативному file store (зокрема хмарному object storage).
- **Кеш і сесії** — MUC (Redis, Memcached, файлові сховища); обробники сесій — file (за замовчуванням), database, Memcached, Redis.
- **Блокування сесій**: стандартна сесія утримує write lock на час запиту. З версії 3.9 (стабільно з 3.11) доступні read-only sessions для сторінок, що не змінюють сесію.

### 1.4 Technical Bottlenecks

1. **Синхронна обробка пікового навантаження.** Важкі операції запиту (старт спроби тесту) виконуються в межах HTTP-запиту. За повідомленнями адміністраторів, вузьким місцем є CPU у момент одночасного старту спроб; для згладжування піку існує плагін `quizaccess_delayed` (рандомізована затримка старту), що підтверджує проблему на рівні Quiz engine.
2. **Залежність фонової обробки від cron.** Мінімальна гранулярність запуску задач визначається інтервалом cron; черга задач зберігається в реляційній БД, а не в спеціалізованому брокері повідомлень.
3. **Спільний файловий `dataroot`** у кластері — розподілене файлове сховище є обов'язковим і стає точкою відмови та обмеженням пропускної здатності.
4. **Session lock contention** — паралельні запити одного користувача серіалізуються блокуванням сесії, якщо не застосовано read-only sessions.
5. **Відсутність real-time каналу в ядрі** — оновлення даних для викладача потребує перезавантаження сторінки або стороннього плагіна.

## 2. Anki

### 2.1 Архітектурний патерн і вплив на масштабованість

Anki — локальний (local-first) настільний застосунок з шаруватою архітектурою:
- **rslib** — бібліотека на Rust, що містить основну частину логіки (планування, робота з колекцією, синхронізація);
- **pylib** — Python-шар, що надає методи backend через приватний модуль-міст `rsbridge` і може використовуватися без GUI;
- **aqt** — графічний інтерфейс на Qt (PyQt) поверх pylib;
- **ts/** — вебкомпоненти на TypeScript, вбудовані в Qt-інтерфейс.

Обчислення розкладу повторень виконуються на клієнті. Серверна частина (AnkiWeb) виконує функцію сховища для синхронізації між пристроями і не бере участі в плануванні. Масштабування в класичному розумінні не потрібне: кожен користувач має власну ізольовану колекцію. Водночас модель не передбачає спільних колекцій для групи чи серверної аналітики.

Алгоритми планування: SM-2 (legacy) і FSRS. FSRS інтегровано в ядро з версії 23.10 як опцію поряд з SM-2; до того він був доступний лише через custom scheduling.

### 2.2 Протоколи передачі даних і взаємодії

- **Між шарами всередині застосунку** — Protocol Buffers (визначення в `proto/anki/`): типізований обмін між Rust, Python і TypeScript. Protobuf-інтерфейс не є публічним API.
- **Синхронізація** — HTTP(S)-протокол синхронізації з AnkiWeb. Протокол не стандартизований і може змінюватися між версіями, тому оновлення клієнтів без оновлення self-hosted сервера може порушити синхронізацію.
- **Self-hosted sync server** вбудовано в Anki з версії 2.1.57 (окрема збірка на Rust — з 2.1.66). Сервер працює по нешифрованому HTTP; для доступу з мережі передбачено VPN або reverse proxy з HTTPS. Розмір payload обмежено 100 MB (параметр `MAX_SYNC_PAYLOAD_MEGS`).
- **Обмін контентом між користувачами** — експорт/імпорт пакетів `.apkg`, а не мережевий API.
- Real-time канал відсутній.

### 2.3 Стек даних і механізми консистентності

- **SQLite**: колекція зберігається в одному файлі `collection.anki2` в каталозі профілю; медіафайли — окремо в `collection.media`.
- **Двонаправлена синхронізація** (normal sync) об'єднує зміни з різних пристроїв. При конфлікті повторень однієї картки обидва повторення зберігаються в історії, а стан картки визначається за останньою відповіддю.
- **Одностороння повна синхронізація** (full sync) застосовується при першій синхронізації та після змін схеми, які неможливо об'єднати (додавання поля, видалення шаблону картки): зберігаються дані лише однієї сторони.
- **Медіа** синхронізується окремим потоком і завжди об'єднується; редагування наявного файлу без зміни імені не виявляється.
- Документація забороняє розміщувати колекцію в мережевих або хмарних синхронізованих каталогах (ризик пошкодження бази SQLite).

### 2.4 Technical Bottlenecks

1. **Клієнтоцентрична модель даних** — відсутня серверна сутність групи, курсу чи ролі викладача; агрегування прогресу кількох користувачів архітектурно не передбачено.
2. **Втрата даних при full sync** — зміна схеми колекції на одному пристрої змушує відкинути зміни іншого.
3. **Планування в межах однієї колекції** — алгоритм (SM-2 або FSRS) обчислює інтервал для кожної картки незалежно; механізму пріоритизації за датами іспитів кількох дисциплін у ядрі немає.
4. **Нестандартизований протокол синхронізації** — сумісність self-hosted сервера залежить від версії клієнта.
5. **Ліміт payload синхронізації** (100 MB за замовчуванням) обмежує обсяг змін, що передаються за одну операцію.

## 3. Quizlet

> [!warning] Закрита система
> Вихідний код і актуальна архітектурна документація Quizlet не публікуються. Офіційних інженерних матеріалів небагато, і вони датовані 2012–2017 роками. Нижче розділено підтверджені факти (з джерелом) і архітектурні припущення.

### 3.1 Архітектурний патерн і вплив на масштабованість

**Підтверджено:**
- За публічно доступними даними (2012), серверну частину побудовано на стеку Apache, PHP, MySQL; для повнотекстового пошуку застосовувався Sphinx Search, для керування конфігурацією серверів — Puppet.
- 1 серпня 2015 року інфраструктуру з 200 машин перенесено на Google Compute Engine. Інфраструктура обслуговує вебсайт і API для мобільних застосунків. Навантаження має виражену сезонність: від літа до осені трафік зростає вшестеро.

**Імовірно:** серверна частина є централізованим вебзастосунком з горизонтально масштабованим рівнем вебсерверів у хмарі. Актуальний поділ на сервіси публічно не підтверджено.

### 3.2 Протоколи передачі даних і взаємодії

**Підтверджено:** HTTP API для мобільних клієнтів (Google Cloud, 2016). Сторонні клієнтські бібліотеки документують публічний REST API 2.0 з автентифікацією OAuth 2.0; поточний статус цього API офіційно не підтверджено.

**Імовірно:** для синхронних групових режимів (Quizlet Live) застосовується постійне двонаправлене з'єднання (WebSocket або аналог). Інженерного опису реалізації в публічному доступі не знайдено.

### 3.3 Стек даних і механізми консистентності

**Підтверджено (Google Cloud, 2017):**
- основна СУБД — MySQL;
- масштабування виконувалося вертикальним шардуванням (окремі таблиці в окремих базах) і перенесенням читання на репліки; за оцінкою компанії, підхід вичерпував можливості, оскільки окремі таблиці перевищували ємність одного шарда MySQL;
- компанія тестувала Cloud Spanner як заміну шардованому MySQL.

**Підтверджено (Google Cloud, 2016):** аналітика production- та event-даних — Google BigQuery; аудіофайли text-to-speech зберігаються в Google Cloud Storage; CDN — Cloudflare.

**Імовірно:** читання з асинхронних реплік MySQL дає eventual consistency для операцій читання після запису (replication lag).

### 3.4 Technical Bottlenecks

1. **Масштабування запису в реляційну СУБД** — публічно підтверджене обмеження: обсяг записів перевищував можливості одного вузла MySQL, вертикальне шардування досягло межі.
2. **Сезонний пік навантаження** — шестикратне зростання трафіку потребує запасу потужностей або автоматичного масштабування.
3. **Імовірно:** алгоритми повторення працюють у межах окремого навчального набору і не координують розклад між кількома дисциплінами з різними датами іспитів (публічної специфікації алгоритму не знайдено).
