# Частина 1. Модель As-Is

## 1. Загальна характеристика домену

Предметною областю є підготовка студентів ІТ-спеціальностей закладу вищої освіти до екзаменаційної сесії та контроль засвоєння навчального матеріалу викладачем. Типовий цикл охоплює семестр тривалістю 16–18 тижнів, протягом якого студент паралельно опановує 5–7 дисциплін; за кожною дисципліною проводиться 12–16 лекційних занять, а підсумковий контроль зосереджено в екзаменаційному періоді тривалістю 2–3 тижні з різними датами складання дисциплін.

З погляду програмної інженерії домен обслуговують два класи систем. Системи управління навчанням (LMS, Learning Management System) реалізують модель «контент — тест — оцінка» із серверним зберіганням результатів і орієнтовані на одноразовий контроль. Застосунки інтервального повторення реалізують модель «картка — відповідь — інтервал» і орієнтовані на індивідуальне запам'ятовування без серверної ролі викладача. Інтеграція між класами систем у типовому навчальному процесі відсутня: дані про результати тестування в LMS не впливають на розклад повторень, а дані про повторення не доступні викладачу.

Станом на 2026 рік для домену характерні такі технологічні тенденції: перехід навчальних сервісів на mobile-first клієнти; інтеграція великих мовних моделей (LLM) у процес створення навчального контенту, зокрема в ядрі Moodle 4.5 з'явилася AI-підсистема з підключенням зовнішніх провайдерів; заміна евристичних алгоритмів планування повторень моделями, що оптимізуються за історією відповідей (FSRS); застосування стандартів інтероперабельності LTI 1.3 та xAPI для обміну даними між навчальними системами.

## 3. Бізнес-процеси та Workflows (As-Is)

### P1. Підготовка студента до сесії з кількох дисциплін

**Поточний стан.** Студент проходить тест у Moodle після вивчення теми. Відповідь передається HTTP-запитом на сервер LMS, результат зберігається в реляційній БД і відображається в журналі оцінок. Після закриття тесту повторне звернення до матеріалу системою не ініціюється. Для довготривалого запам'ятовування студент самостійно переносить матеріал у застосунок інтервального повторення (Anki, Quizlet): картки створюються вручну або імпортуються, розклад повторень обчислюється на клієнті окремо для кожної колоди.

**Потоки даних.** Moodle: клієнт → HTTP → PHP-сервер → БД → журнал оцінок. Anki: локальна SQLite → алгоритм SM-2/FSRS на пристрої → синхронізація з AnkiWeb. Обміну даними між двома контурами немає.

**Вузькі місця (bottlenecks):**
- результат тестування в LMS не змінює жодного стану повторення: інформація про помилки студента втрачається для планування;
- ручне перенесення контенту між системами — операція без валідації, з ризиком розбіжності версій матеріалу;
- розклад повторень у кожній колоді обчислюється незалежно, без вхідного параметра «дата іспиту»; пріоритизація між 5–7 дисциплінами виконується студентом вручну;
- у пікові тижні сесії кількість запланованих повторень зростає без урахування доступного часу, що призводить до накопичення простроченої черги.

### P2. Контроль засвоєння матеріалу групою

**Поточний стан.** Викладач отримує дані про засвоєння зі звітів тесту в LMS. Звіт формується на запит (pull-модель): для отримання актуального стану сторінку потрібно оновити. Агрегування результатів за темами між кількома тестами виконується вручну або експортом у табличний редактор. Дані про самостійне повторення студентів у сторонніх застосунках викладачу недоступні.

**Потоки даних.** Студент → HTTP → БД LMS → (запит викладача) → HTML-звіт або експорт CSV/XLSX → ручна обробка.

**Вузькі місця (bottlenecks):**
- відсутність push-каналу: час від відповіді студента до її появи у викладача визначається частотою ручних оновлень, а не подією;
- агрегування «студент × тема» вимагає ручних операцій експорту, тож кількість операцій зростає лінійно з кількістю тестів;
- фонова обробка в LMS прив'язана до запуску cron, тому похідні дані (наприклад, перерахунок оцінок) оновлюються з затримкою інтервалу cron;
- відсутній формалізований механізм підтвердження засвоєння теми викладачем, окремий від оцінки за тест.

### P3. Формування банку тестових завдань

**Поточний стан.** Викладач створює тестові завдання вручну в редакторі банку питань LMS або імпортує їх у форматах GIFT, Moodle XML чи Aiken. Для курсу з 12–16 лекцій формування банку з 10–20 питань на лекцію становить 120–320 завдань на дисципліну. Генерація тестових завдань за допомогою LLM у ядрі LMS не передбачена й доступна лише через сторонні плагіни або ручне копіювання результатів зовнішнього чат-інтерфейсу.

**Потоки даних.** Лекційний матеріал (PDF) → ручне формулювання завдань → редактор або файл імпорту → БД LMS.

**Вузькі місця (bottlenecks):**
- трудомісткість ручного формування банку є основним обмеженням обсягу контрольних матеріалів;
- при використанні LLM через зовнішній інтерфейс відсутні валідація структури відповіді, журнал запитів і контроль вартості;
- синхронний виклик зовнішнього LLM API в межах HTTP-запиту користувача передає Latency провайдера (від одиниць до десятків секунд) і його збої безпосередньо на клієнт;
- відсутній статусний конвеєр «чернетка → модерація → публікація», тому неперевірений згенерований контент може потрапити до студентів.

## 4. Регуляторні та індустріальні обмеження

- **Захист персональних даних.** Обробка даних студентів регулюється Законом України «Про захист персональних даних» № 2297-VI; як орієнтир для мінімізації даних і права на видалення застосовано принципи GDPR (Регламент ЄС 2016/679). Наслідки для системи: мінімізація полів профілю, можливість псевдоніма, контроль доступу до результатів за роллю.
- **Академічна доброчесність.** Закон України «Про освіту» (ст. 42) визначає вимоги академічної доброчесності. Наслідки: рандомізація порядку питань і відповідей, журнал дій із контентом, обов'язкова модерація згенерованих матеріалів викладачем.
- **Використання ШІ в освіті.** Регламент ЄС про штучний інтелект (AI Act, 2024/1689) відносить системи ШІ для оцінювання результатів навчання до категорії високого ризику з вимогою людського нагляду. Для системи без юрисдикційної дії регламенту його положення застосовано як орієнтир: LLM використовується лише для генерації чернеток, оцінювання й публікація контенту залишаються за викладачем.
- **Безпека застосунків.** Рекомендації OWASP Top 10 та OWASP ASVS: контроль доступу на рівні ресурсу, захист автентифікації, валідація вхідних даних і файлів.
- **Якість ПЗ.** Модель якості ISO/IEC 25010 використано як класифікатор нефункціональних вимог (продуктивність, безпека, надійність, супроводжуваність).
- **Інтероперабельність.** Стандарти LTI 1.3 (1EdTech) і xAPI визначають інтеграцію із LMS закладу; в межах MVP інтеграцію не реалізовано, її враховано як напрям розвитку.
- **Технологічні обмеження.** Rate limit і тарифікація LLM API за токенами; бюджет проєкту, близький до нуля; соло-розробка тривалістю 6 місяців.

# Частина 2. Модель To-Be та вимоги

## 5. Концептуальна модель To-Be

Цільовий стан передбачає об'єднання тестування, планування повторень і контролю засвоєння в одному програмному контурі з єдиним джерелом даних у PostgreSQL.

**P1 To-Be.** Кожна відповідь студента в межах однієї транзакції зберігається як Answer і перераховує ReviewState теми за алгоритмом SM-2 (коефіцієнт легкості EF, інтервал, кількість повторень). Персональний план на день формується сервером із ReviewState усіх курсів студента з пріоритизацією за датою іспиту кожної дисципліни та обмеженням денного обсягу. Ручне перенесення контенту між системами вилучено з процесу.

**P2 To-Be.** Після фіксації відповіді backend публікує подію прогресу в кімнату курсу Socket.io; дашборд викладача оновлюється без запиту з боку клієнта. Агрегат «студент × тема» обчислюється на сервері й відображається як теплова карта. Підтвердження засвоєння фіксується окремою дією викладача (confirmed_by) з журналюванням.

**P3 To-Be.** Викладач завантажує PDF лекції; REST-ендпоінт валідує файл і повертає 202 Accepted з ідентифікатором задачі, не очікуючи відповіді LLM. Задача ставиться в чергу BullMQ на Redis; worker-процес виконує парсинг, виклик Claude API, валідацію JSON-структури і зберігає результат як Draft зі статусом pending. Невдалі задачі повторюються з експоненційною затримкою, після вичерпання спроб переходять у dead-letter queue. Публікація відбувається лише після схвалення викладачем.

Наслідком є перехід від pull-моделі до подієвої для моніторингу, від клієнтського до серверного планування повторень і від синхронного до асинхронного виклику LLM.

## 6. Функціональні вимоги (Core Features)

**Модуль автентифікації та доступу**
- FR-1. Реєструвати користувача, автентифікувати його за парою access/refresh JWT і призначати роль окремо для кожного курсу (owner, co-instructor, student) з приєднанням за кодом запрошення.

**Модуль курсів і контенту**
- FR-2. Створювати курс із переліком тем і датою іспиту; приймати завантаження лекційних матеріалів у форматі PDF з перевіркою типу й розміру.

**Модуль тестування**
- FR-3. Видавати тест із рандомізованим порядком питань і відповідей, фіксувати відповідь та обчислювати оцінку якості відповіді за шкалою 0–5.

**Модуль планування повторень**
- FR-4. Перераховувати стан повторення теми за алгоритмом SM-2 після кожної відповіді в межах однієї транзакції з її збереженням.
- FR-5. Формувати персональний план на день з урахуванням усіх курсів студента, пріоритизуючи теми за близькістю дати іспиту та простроченням повторення.

**Модуль асинхронної генерації та модерації контенту**
- FR-6. Ставити задачу генерації тесту за лекційним матеріалом у чергу, виконувати її worker-процесом через Claude API з валідацією структури результату та зберігати чернетку; надавати викладачу дії схвалення, редагування й відхилення чернетки.

**Модуль моніторингу та аналітики**
- FR-7. Транслювати події прогресу студентів у кімнату курсу через WebSocket і відображати дашборд групи в реальному часі.
- FR-8. Обчислювати та відображати теплову карту засвоєння «студент × тема» і фіксувати підтвердження засвоєння теми викладачем.

> [!note] Межі MVP
> Сценарний тренажер рішень реалізується в межах модуля FR-6 як другий тип генерованого контенту з тим самим конвеєром модерації. Push-нагадування, офлайн-режим та інтеграція LTI 1.3 до Core Features не включено.

## 7. Нефункціональні вимоги (NFRs)

Цільове навантаження визначено для сценарію апробації: один потік до 100 студентів, до 50 одночасних сесій, пікова інтенсивність 50 RPS (одночасний старт тестування групою). Метрики продуктивності перевіряються навантажувальним тестуванням k6 на конфігурації docker-compose.

## 8. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка кросплатформної клієнт-серверної системи на основі модульного моноліту з асинхронною чергою задач і двонаправленим каналом передачі подій для вирішення задачі адаптивної підготовки студентів ІТ-спеціальностей до екзаменаційної сесії з кількох дисциплін. Система має забезпечити серверне планування інтервального повторення за алгоритмом SM-2 з пріоритизацією за датами іспитів, асинхронну генерацію тестових завдань великою мовною моделлю з обов'язковою модерацією викладачем і моніторинг засвоєння групою в реальному часі за протоколом WebSocket з дотриманням метрик таблиці 3 (p95 Latency REST API ≤ 300 мс при 50 RPS, доставка подій ≤ 1 с, обробка задач генерації ≤ 90 с з повторними спробами і dead-letter queue).
