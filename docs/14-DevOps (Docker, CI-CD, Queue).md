# DevOps (Docker, CI/CD, Queue)

Додано свідомо поверх мінімального MVP —  архітектурну складність рівня F2 ("Просто CRUD-сайти не приймаються"). Це точкові, реалістичні за часом доповнення, а не повна enterprise-інфраструктура.

## Контейнеризація — Docker + docker-compose

Сервіси в `docker-compose.yml`:
- `backend` (Node.js + Express)
- `postgres` (БД)
- `redis` (черга)
- (опційно) `worker` — окремий контейнер для обробки чергу генерації сценаріїв, якщо винести з основного backend-процесу

**Навіщо**: відтворюваність середовища, легкий локальний запуск (`docker-compose up`), природний крок до подальшого деплою.

## CI/CD — GitHub Actions

Базовий пайплайн `.github/workflows/ci.yml`, що запускається на кожен push/PR:
1. Встановлення залежностей
2. Лінт (ESLint)
3. Тести (базові unit-тести backend — наприклад, логіка SM-2-розрахунку, парсинг JSON від LLM)

**Навіщо**: демонструє інженерну культуру (Conventional Commits + CI), пряма вимога рубрики ЛР№1 щодо "історії комітів, що демонструє культуру роботи з Git".

## Черга повідомлень — Redis + BullMQ

Детальний опис використання — [[08-Кілер-фіча (сценарії))#Конвеєр генерації та курації контенту]].

Коротко: AI-генерація сценарію йде через чергу, а не прямий синхронний виклик Claude API — асинхронність, retry при збоях, контроль паралельних запитів.

## Що свідомо НЕ додається (щоб не роздувати обсяг)

- Kubernetes — для одного backend-сервісу без масштабування це надмірно
- Мікросервісна архітектура — застосунок залишається монолітом (Node.js + Express), чергу використовуємо для асинхронності конкретної задачі, а не як привід ділити на сервіси
- Observability-стек (Prometheus/Grafana) — можна згадати як "перспективу розвитку" в дипломній, не реалізовувати
