# Специфікація вимог (SRS)

> [!info] PKM-копія [srs.md](srs.md) (Додаток А пояснювальної записки). Джерело істини — srs.md.

Специфікацію вимог до програмного забезпечення складено за структурою стандарту ISO/IEC/IEEE 29148:2018 [49]. Джерела вимог: функціональні вимоги FR-1…FR-8 і нефункціональні вимоги NFR-01…NFR-14 з аналізу предметної області, бізнес-вимоги BR-01…BR-21 і бізнес-правила Rule-01…Rule-04, вимоги доступності NFR-12, NFR-13 з переліку нефункціональних вимог, відгук наукового керівника від 05.11.2026. Версію сформовано за результатами аудиту вимог (протокол — [17-AI Insights.md](17-AI%20Insights.md), Запис 11) і доповнено рішеннями автора перед ЛР6 (Запис 16).

**Атрибути вимог.** Кожна вимога має ідентифікатор, джерело, пріоритет і метод верифікації.

- Пріоритет: **Must** — обов'язкова для MVP; **Should** — реалізується в MVP за наявності часу, не блокує апробацію; **Won't (MVP)** — поза межами MVP, ідентифікатор збережено для трасування.
- Метод верифікації (ISO/IEC/IEEE 29148, п. 6.5): **T** — тестування (Test), **D** — демонстрація (Demonstration), **I** — інспекція (Inspection), **A** — аналіз (Analysis).
- Модальне дієслово «повинна» («повинен») позначає обов'язкову вимогу.

## 1. System Context

### 1.1. Призначення системи

Recall — кросплатформна клієнт-серверна система адаптивної підготовки студентів ІТ-спеціальностей до екзаменаційної сесії з кількох дисциплін. Система поєднує тестування, серверне планування інтервального повторення за алгоритмом SM-2, асинхронну генерацію тестових завдань великою мовною моделлю з модерацією викладачем, пробні тести до контрольних заходів і моніторинг засвоєння групою в реальному часі.

### 1.2. Межі системи (Scope)

**У межах MVP:**

- автентифікація за корпоративною поштою закладу з підтвердженням пошти і відновленням доступу листом; рольова модель на рівні курсу (owner, co-instructor, student);
- курси, теми, контрольні заходи, завантаження лекційних матеріалів і закритих зразків тестів у форматі PDF;
- тестування з рандомізацією, серверним таймером і перерахунком стану повторення за SM-2;
- персональний план на день з пріоритизацією між курсами за найближчим контрольним заходом;
- асинхронна генерація тестів і тренувальних питань через Claude API з модерацією;
- пробний тест до контрольного заходу;
- фіксація виходу із застосунку, блокування знімків екрана і копіювання під час тесту;
- панель моніторингу викладача в реальному часі і теплова карта засвоєння;
- кодова база мобільного клієнта, спільна для Android та iOS (Expo); ручна верифікація MVP виконується на Android.

**Поза межами MVP:**

- інтеграція з LMS закладу за стандартом LTI 1.3;
- офлайн-режим роботи клієнта;
- публікація застосунку в Google Play і App Store;
- серверні push-сповіщення і нагадування про повторення (BR-06);
- сценарний тренажер прийняття рішень: генерація, проходження і перегляд шляху рішень сценаріїв (BR-09…BR-11, напрям розвитку);
- флагманський модуль базових інженерних навичок із серією днів практики (streak) (BR-15, напрям розвитку);
- вхід через систему єдиного входу закладу (OpenID Connect, Google Workspace або Microsoft 365) — напрям розвитку;
- ручна верифікація на пристроях iOS (сценарії VER-16, VER-24, VER-25 у частині iOS).

### 1.3. Зовнішні актори та системи

| Актор / система | Тип | Взаємодія із системою |
|---|---|---|
| Студент | Людина | Проходить тести і пробні тести, виконує план повторення, переглядає власний прогрес |
| Викладач — власник курсу (owner) | Людина | Створює курс, теми і контрольні заходи, завантажує матеріали і зразки тестів, модерує чернетки, запрошує учасників, переглядає панель моніторингу |
| Співвикладач (co-instructor; значення ENUM `co_instructor`) | Людина | Додає контент, модерує чернетки, переглядає панель моніторингу, підтверджує засвоєння; не керує складом викладачів і не видаляє курс |
| Claude API (Anthropic) | Зовнішня система | Генерує чернетки тестових завдань, сценаріїв і тренувальних питань за запитом worker-процесу (Messages API, HTTPS) |
| SMTP-провайдер | Зовнішня система | Доставляє листи підтвердження корпоративної пошти і відновлення доступу (SMTP, порт 587, STARTTLS) |
| Мобільна ОС (Android, iOS) | Зовнішня система | Надає події стану застосунку (AppState), механізм захисту екрана, захищене сховище ключів (Keystore, Keychain), служби читання екрана TalkBack і VoiceOver |

### 1.4. Обмеження

- Соло-розробка тривалістю 6 місяців.
- Розгортання в docker-compose на одному хості; хмарний бюджет відсутній.
- Цільове навантаження: один потік до 100 студентів, до 50 одночасних сесій, пікова інтенсивність 50 RPS.
- Тарифікація Claude API за токенами і обмеження rate limit провайдера.

### 1.5. Припущення та залежності

- Генерація контенту залежить від доступності Claude API; ідентифікатор моделі (`claude-haiku-5-5`, обґрунтування — ADR-001) фіксується в конфігурації worker-процесу і не змінюється без оновлення JSON-схем і повторної перевірки.
- Тарифний рівень облікового запису Claude API забезпечує щонайменше 2 одночасні запити (SRS-NFR-ASYNC-04).
- Під час апробації студенти і викладачі мають стабільне з'єднання з інтернетом; короткочасна втрата з'єднання обробляється вимогами SRS-FUN-16 і SRS-FUN-38.
- Студенти і викладачі мають корпоративну поштову адресу закладу; заклад надає або дозволяє використання поштового сервера SMTP для доставки службових листів.
- Мобільні пристрої учасників апробації відповідають SRS-NFR-COMP-01.

## 2. Functional Requirements

### 2.1. Автентифікація та доступ

<a id="srs-fun-01"></a>**SRS-FUN-01.** Система повинна реєструвати користувача за корпоративною поштою закладу, ім'ям або псевдонімом і паролем довжиною від 10 до 128 символів; домен пошти перевіряється за переліком дозволених доменів зі змінної конфігурації `ALLOWED_EMAIL_DOMAINS` (за замовчуванням `chnu.edu.ua`), пошта з іншим доменом → 422. Запит реєстрації завжди повертає 202: для наявної пошти (без урахування регістру) обліковий запис не змінюється, а на пошту надсилається лист «обліковий запис уже існує» з посиланням на відновлення пароля; лист надсилається після відповіді, тому ні код, ні час відповіді не розкривають існування облікового запису. Після реєстрації система надсилає на пошту одноразове посилання підтвердження зі строком дії 24 год; токен передається у фрагменті URL посилання (`#token=…`), який не надсилається на сервер. До підтвердження пошти вхід з правильним паролем відхиляється з кодом 403; невірний пароль дає 401 незалежно від стану пошти.
*Джерело: FR-1 · Пріоритет: Must · Метод: T*

<a id="srs-fun-02"></a>**SRS-FUN-02.** Система повинна автентифікувати користувача з підтвердженою поштою за корпоративною поштою і паролем та видавати пару access/refresh JWT з параметрами SRS-NFR-SEC-01 і SRS-NFR-SEC-02.
*Джерело: FR-1 · Пріоритет: Must · Метод: T*

<a id="srs-fun-03"></a>**SRS-FUN-03.** Система повинна призначати користувачу роль окремо в кожному курсі (owner, co-instructor, student); користувач, що створив курс, отримує роль owner.
*Джерело: FR-1, BR-01, Rule-02 · Пріоритет: Must · Метод: T*

<a id="srs-fun-53"></a>**SRS-FUN-53.** Система повинна на запит користувача завершувати сесію: відкликати всі refresh-токени сімейства поточної сесії (family_id); наступне оновлення токена цим сімейством повертає 401.
*Джерело: FR-1, OWASP ASVS V3 · Пріоритет: Must · Метод: T*

<a id="srs-fun-55"></a>**SRS-FUN-55.** Система повинна відновлювати доступ до облікового запису через корпоративну пошту: запит відновлення завжди повертає 202 незалежно від існування облікового запису; на підтверджену пошту надсилається одноразове посилання зі строком дії 30 хв і токеном у фрагменті URL (`#token=…`), який не надсилається на сервер; токен посилання зберігається лише як хеш SHA-256 і анулюється після використання; встановлення нового пароля відкликає всі refresh-токени користувача; новий запит відновлення анулює попередні невикористані токени користувача; лист надсилається після відповіді, тому час відповіді не залежить від існування облікового запису.
*Джерело: FR-1, OWASP ASVS V2.5 · Пріоритет: Must · Метод: T*

<a id="srs-fun-54"></a>**SRS-FUN-54.** Система повинна повертати користувачу з роллю student лише власні спроби, відповіді і події антисписування; запит до спроби іншого користувача того самого курсу повертає 404, до ресурсу іншого курсу — 403.
*Джерело: FR-3, OWASP API Security Top 10 2023, API1 · Пріоритет: Must · Метод: T*

<a id="srs-fun-04"></a>**SRS-FUN-04.** Система повинна створювати на запит owner код запрошення до курсу з роллю, що призначається (co-instructor або student), строком дії (за замовчуванням 7 днів) і можливістю відкликання.
*Джерело: BR-03 · Пріоритет: Must · Метод: T*

<a id="srs-fun-05"></a>**SRS-FUN-05.** Система повинна приєднувати користувача до курсу з роллю коду запрошення лише за умови, що код існує, не відкликаний і строк його дії не минув.
*Джерело: BR-03, Rule-01 · Пріоритет: Must · Метод: T*

<a id="srs-fun-06"></a>**SRS-FUN-06.** Система повинна відхиляти з кодом 403 запити co-instructor на видалення курсу, зміну складу викладачів і зняття ролі owner.
*Джерело: Rule-04 · Пріоритет: Must · Метод: T*

### 2.2. Курси, контент і контрольні заходи

<a id="srs-fun-07"></a>**SRS-FUN-07.** Система повинна створювати курс із назвою дисципліни та впорядкованим переліком тем.
*Джерело: FR-2, BR-02 · Пріоритет: Must · Метод: T*

<a id="srs-fun-08"></a>**SRS-FUN-08.** Система повинна створювати в курсі контрольні заходи типів current (поточний), module (модульний), credit (заліковий) і exam (екзаменаційний) з датою та переліком тем цього курсу.
*Джерело: BR-21 · Пріоритет: Must · Метод: T*

<a id="srs-fun-09"></a>**SRS-FUN-09.** Система повинна приймати від owner або co-instructor лекційний матеріал у форматі PDF з обмеженнями SRS-NFR-SEC-07 і SRS-FUN-51 і прив'язкою до теми курсу.
*Джерело: FR-2, BR-12 · Пріоритет: Must · Метод: T*

<a id="srs-fun-51"></a>**SRS-FUN-51.** Система повинна до збереження PDF і до постановки задачі генерації вилучати текстовий шар документа і відхиляти з кодом 422: документ без текстового шару (тип помилки `pdf-no-text-layer`); документ, що містить понад 60 сторінок або понад 40 000 токенів вилученого тексту (тип помилки `pdf-too-long`). Кількість токенів оцінюється як ⌈кількість символів / 3⌉.
*Джерело: FR-2, SRS-NFR-COST-02 · Пріоритет: Must · Метод: T*

<a id="srs-fun-10"></a>**SRS-FUN-10.** Система повинна приймати від owner або co-instructor зразок тесту у форматі PDF з обмеженнями SRS-NFR-SEC-07 і SRS-FUN-51 і прив'язкою до контрольного заходу курсу.
*Джерело: BR-16 · Пріоритет: Must · Метод: T*

<a id="srs-fun-11"></a>**SRS-FUN-11.** Система повинна не повертати вміст зразка тесту користувачу з роллю student через жоден endpoint REST API і жодну подію WebSocket.
*Джерело: BR-16 · Пріоритет: Must · Метод: T*

<a id="srs-fun-12"></a>**SRS-FUN-12.** Система повинна журналювати дії з контентом (створення, редагування, схвалення, відхилення, видалення) з ідентифікатором користувача, ідентифікатором об'єкта і часом дії.
*Джерело: регуляторні обмеження (академічна доброчесність) · Пріоритет: Must · Метод: T*

### 2.3. Тестування

<a id="srs-fun-13"></a>**SRS-FUN-13.** Система повинна видавати тест із рандомізованим порядком питань і рандомізованим порядком варіантів відповіді в кожному питанні.
*Джерело: FR-3, BR-04 · Пріоритет: Must · Метод: T*

<a id="srs-fun-14"></a>**SRS-FUN-14.** Система повинна передавати на клієнт питання без ознаки правильної відповіді; правильність відповіді визначає лише сервер.
*Джерело: BR-20 (базові механізми антисписування) · Пріоритет: Must · Метод: T*

<a id="srs-fun-15"></a>**SRS-FUN-15.** Система повинна вести серверний таймер спроби тесту і відхиляти відповіді, отримані після закінчення ліміту часу спроби. Ліміт часу спроби: для пробного тесту — ліміт часу зразка (SRS-FUN-34); для режимів daily_plan і practice — 2 хв на кожне питання спроби, не більше 60 хв. Спроба, ліміт часу якої минув, завершується автоматично не пізніше ніж через 1 хв після закінчення ліміту зі статусом expired, оновленням ReviewState за SRS-FUN-19 і публікацією події завершення спроби в кімнату курсу кожного питання спроби; запит на нову спробу того самого режиму за наявності незавершеної спроби з чинним лімітом часу відхиляється з кодом 409 з ідентифікатором незавершеної спроби для її продовження.
*Джерело: BR-18, BR-20 · Пріоритет: Must · Метод: T*

<a id="srs-fun-16"></a>**SRS-FUN-16.** Система повинна фіксувати відповідь ідемпотентно за ключем (attemptId, questionId): повторне надсилання відповіді на те саме питання в тій самій спробі не створює нового запису.
*Джерело: FR-3 · Пріоритет: Must · Метод: T*

<a id="srs-fun-17"></a>**SRS-FUN-17.** Система повинна обчислювати оцінку якості q для кожної теми, що була в спробі, за часткою правильних відповідей з цієї теми за таблицею А.1.
*Джерело: FR-3 · Пріоритет: Must · Метод: T*

Таблиця А.1 – Відображення частки правильних відповідей з теми в оцінку якості q

| p (частка правильних) | q |
|---|---|
| p ≥ 0,9 | 5 |
| 0,75 ≤ p < 0,9 | 4 |
| 0,6 ≤ p < 0,75 | 3 |
| 0,4 ≤ p < 0,6 | 2 |
| 0 < p < 0,4 | 1 |
| p = 0 або немає відповідей | 0 |

Питання без відповіді зараховуються як неправильні. Одна спроба дає рівно одне оновлення ReviewState теми, що відповідає моделі SM-2 — одне повторення елемента за інтервал.

<a id="srs-fun-18"></a>**SRS-FUN-18.** Мобільний клієнт повинен перед початком спроби тесту інформувати студента про фіксацію виходів із застосунку і знімків екрана.
*Джерело: принцип прозорості обробки персональних даних (Закон № 2297-VI, GDPR) · Пріоритет: Must · Метод: D*

### 2.4. Планування повторень

<a id="srs-fun-19"></a>**SRS-FUN-19.** Система повинна після завершення спроби (тестування або пробного тесту) один раз перераховувати ReviewState кожної пари «студент × тема», що була в спробі (EF, інтервал, кількість повторень, дата наступного повторення), за алгоритмом SM-2 з початковим EF = 2,5 і мінімальним EF = 1,3; оцінку якості q для теми обчислювати за часткою правильних відповідей з цієї теми в спробі (табл. А.1).
*Джерело: FR-4, BR-05, BR-18 · Пріоритет: Must · Метод: T*

<a id="srs-fun-20"></a>**SRS-FUN-20.** Система повинна формувати персональний план на день з тем-кандидатів усіх курсів студента, упорядкованих за спаданням пріоритету P := d_overdue + 10 / max(1, d_event), де d_overdue — кількість днів прострочення повторення (0, якщо дата повторення не минула), d_event — кількість днів від сьогодні до найближчого контрольного заходу з датою не раніше сьогодні, що містить тему; для теми без такого заходу другий доданок дорівнює 0. Тема є кандидатом, якщо next_review ≤ сьогодні OR (d_event ≤ 14 AND mastery < 0,8), де mastery — засвоєння за SRS-FUN-46; тема, усі контрольні заходи якої минули і next_review > сьогодні, кандидатом не є. Тема без ReviewState вважається такою, що має next_review = сьогодні і mastery = 0. Поточна дата («сьогодні») визначається в часовому поясі Europe/Kyiv; ту саму дату використовує обчислення next_review за SRS-FUN-19.
*Джерело: FR-5, BR-13, BR-21 · Пріоритет: Must · Метод: T*

<a id="srs-fun-21"></a>**SRS-FUN-21.** Система повинна обмежувати персональний план на день 30 питаннями і розподіляти їх між темами-кандидатами пропорційно P з обмеженням не менше 2 і не більше 8 питань на тему; до плану входять не більше 15 тем-кандидатів з найбільшим P (30 / 2); якщо сума P тем плану дорівнює 0, питання розподіляються між ними рівномірно. *Джерело: модель To-Be процесу P1 · Пріоритет: Must · Метод: T*

## 5. Glossary

| Термін | Визначення |
|---|---|
| SM-2 | Алгоритм інтервального повторення SuperMemo-2 (P. Woźniak, 1987), який за оцінкою якості відповіді q ∈ {0…5} обчислює інтервал до наступного повторення і коефіцієнт легкості; при q < 3 лічильник повторень скидається, інтервал повертається до 1 дня, EF не змінюється (як в оригінальному описі алгоритму, [Woźniak, 1990](./5_references.md)) |
| Argon2id | Функція хешування паролів (RFC 9106) зі стійкістю до атак на GPU за рахунок параметра пам'яті m; параметри: m — пам'ять у KiB, t — кількість проходів, p — ступінь паралелізму |
| Ease Factor (EF) | Коефіцієнт легкості SM-2, що визначає множник інтервалу: EF′ = EF + (0,1 − (5 − q) · (0,08 + (5 − q) · 0,02)); початкове значення 2,5, мінімальне 1,3; застосовується лише при q ≥ 3 |
| p95 Latency | 95-й перцентиль часу відповіді: значення, яке не перевищують 95 % вимірів за інтервал тестування |
| BullMQ | Бібліотека черг задач для Node.js, що зберігає стан задач у Redis і підтримує повторні спроби, відкладене виконання та обмеження паралелізму обробників |
| Dead-letter queue | Сховище задач, обробку яких завершено помилкою після вичерпання допустимої кількості спроб; задачі в ньому автоматично не повторюються і підлягають ручному аналізу; у BullMQ реалізується станом failed із збереженою причиною збою |
| Корпоративна пошта | Поштова адреса в домені закладу освіти, виданого студенту або викладачу; підтверджує належність користувача до закладу і є ідентифікатором облікового запису |
| JWT | JSON Web Token (RFC 7519) — підписаний токен із набором тверджень (claims), що передає ідентичність і строк дії сесії без звернення до сховища сесій |
| WebSocket | Протокол повнодуплексного обміну повідомленнями поверх одного TCP-з'єднання, встановленого через HTTP Upgrade (RFC 6455); у системі використовується через бібліотеку Socket.io з механізмом кімнат |
